# Vase Architecture v3

> **Vase 是一个 C++20 插件管理能力库。**
> 它不提供业务逻辑，不提供编辑器，不提供游戏引擎适配。
> 它只负责：发现插件、解析依赖、装配、运行、局内受控装卸、干净关停。

**文档状态**：设计文档（v3，2026-09-16）。仓库处于脚手架阶段（M0 构建地基），尚无任何架构代码。
**v3 相对 v2 的主题变更只有一个：热插拔**——经需求方确认取**档 ①**（局内仅装卸「无人依赖」的叶插件），分层主干保留；v2 全文见 git 历史（提交 `5423a77`）。逐条变更见 [1.5](#15-v3-变更总览相对-v2)。
本文中的接口签名与文件格式仍为**提议**，不是既有实现；**目录布局已确认**（第 10 节，其中 `Session → Pod` 的实体更名待 M1 落地）。未经需求方确认的内容一律不作为既定事实——凡未落成代码的，其状态以第 13 节的分类为准。

## 0. 定位与设计原则

### 0.1 边界

Vase 是**能力库**，不是框架、不是平台、不是运行时环境。它被宿主嵌入。

| Vase 负责 | Vase 不负责 |
|---|---|
| 发现插件、解析清单 | 用什么 UI 展示插件列表 |
| 解析依赖、计算加载计划 | 关卡、资产、窗口、输入 |
| 加载、卸载、**局内受控装卸**（5.6）插件二进制 | 业务逻辑（战斗、AI、渲染……） |
| 服务注册与解析 | 游戏引擎适配（UE / Unity / Godot） |
| 事件派发 | 构建系统本身 |
| 副作用的回收与生命周期保证 | 什么时候编译、什么时候重启进程 |
| 诊断：泄漏、残留、契约违背 | 运行参数（地图、种子、时间缩放……） |

宿主可以是编辑器、游戏本体、命令行工具、测试装置。Vase 不假设宿主的形态。

### 0.2 核心承诺

> **每一次运行（Pod）都能干净地起、干净地灭、可重复无数次；灭之前，任何叶插件可以随时进出，而每一次进出都必须有账可查。**

这条承诺是 Vase 全部设计约束的来源。它比「支持动态加载」强得多：「能加载」是容易的，「能干净卸载并且下次如同首次」才是难的。文档后面每一条看似繁琐的纪律（Effect 唯一注册通道、进程级状态必须登记、逆序回收、诊断基线），都是为了让这条承诺**可证明**而不是**可祈祷**。v3 把「随时进出」也纳入承诺，代价是它必须同样可证明——它的来源是依赖账本（5.6）：**进出不是许可，是结算。**

### 0.3 设计原则

1. **生命周期由 Vase 完全拥有。** 插件不管理自己的销毁——它把一切注册交给 Vase，Vase 在正确的时机一次性回收。
2. **一切注册都是可回收的。** 服务、事件、定时器，以及宿主自定义的注册入口——没有例外，没有「这个不用管」的注册。
3. **元数据与二进制分离。** 清单可以被读取而不必加载代码；这样才能在不冒崩溃风险的前提下枚举、求解、展示。
4. **失败不致命。** 单个插件加载失败，整局照常运行，失败的插件被报告而非导致崩溃。
5. **承诺必须可验证。** 凡是无法被测试证伪的承诺，不作为承诺写进本文。而**无法机制化的承诺，一律显式标注为「契约束」**（见 9.3），不混进「保证」里。
6. **跨边界的一切值都是借用。** 所有权不转移，接收方不得留存——不保存引用，也不保存其中任何视图（`string_view`、`const char*`）。这条在本文出现四次（事件对象、`Error::Message`、配置值、宿主拿到的服务指针），所以提为通则：**边界上只传「当下有效」的东西。**
7. **不使用 C++ 异常。** 全项目以**关闭异常**的方式编译（Windows `/EHs-c-`、Linux/macOS `-fno-exceptions`）。错误一律经 `Result<T>` / `Error` 显式返回，不抛。这条不只服务于 ABI——8.3 那条「异常不得穿过插件边界」在关掉异常之后是**编译期**强制的，而不是靠约定；它同时也让 0.2 的承诺更容易证明：没有一条控制流能从插件镜像里「跳」回宿主。代价是一批标准库与第三方库的抛错路径必须改走不抛的形式，清单见 13.2，遗留的契约束见 13.3。

## 1. 分层模型

Vase 由三层构成，各层生命周期不同、职责正交。

```text
┌─────────────────────────────────────────────────────────┐
│ PluginCatalog          元数据层                          │
│   · 扫描目录、解析 .plugin.json                          │
│   · 静态求解依赖、计算加载计划                            │
│   · 不加载任何二进制                                      │
│   · 可被 VaseCli / 编辑器 / 装配期共同复用                │
└────────────────────────┬────────────────────────────────┘
                         │ 计划
┌────────────────────────▼────────────────────────────────┐
│ PluginHost             二进制层（进程级）                 │
│   · 拥有已加载的插件二进制                                │
│   · 创建 / 销毁 Pod；Adopt / Eject 叶插件（5.6）          │
│   · 依赖账本：解析落账、Eject 执法（边带 Pod 归属）        │
│   · 进程级状态登记与诊断                                  │
└────────────────────────┬────────────────────────────────┘
                         │ 实例
┌────────────────────────▼────────────────────────────────┐
│ Pod                    执行层（实例级）                   │
│   · 服务注册表、事件总线                                  │
│   · 插件实例与 EffectScope                               │
│   · 一局的一切都在这里；销毁即归零，局内进出凭账（5.6）     │
└─────────────────────────────────────────────────────────┘
```

### 1.1 为什么要分三层

每一层都能被单独使用，这是分层成立的判据：

| 使用方 | 用到的层 | 用途 |
|---|---|---|
| `VaseCli` | Catalog | 校验清单、生成索引、报告依赖问题——从不加载任何 DLL |
| 编辑器 | Catalog | 画插件列表、画配置面板、实时提示「禁用它会导致谁被跳过」——同样不加载 DLL |
| 游戏本体 | Catalog + Host + Pod | 启动时装配一次，跑一局，退出 |
| 编辑器 / 测试装置 | Host + Pod | 反复创建销毁 Pod；**局内热装卸叶插件**（5.6、8.1） |

关键收益：**元数据操作完全不需要触碰二进制。** 二进制是会失败、会崩溃、会锁文件的东西；把它挡在「画界面」和「算依赖」之外，工具链就能做得又快又稳。

### 1.2 铁律

> **实例级对象不得被进程级对象持有。** 反向（实例级引用进程级）允许。

这是「干净关停」的全部依据。如果某个进程级的容器里存了一个 Pod 内的对象，那个 Pod 就永远无法真正归零——它的残留会被下一次 Pod 看见，于是「每一次运行都如同首次」不成立。

Debug 构建下由**实例归属追踪器**抓违规：Vase 自己拥有的 Pod 级对象（服务、插件实例、EffectScope）带属主标记，`PluginHost` 的进程级容器在插入时断言属主为空或为进程级。

**必须说清它的覆盖范围，否则会高估这条铁律的保障。** 追踪器只看得住 **Vase 自己的容器**——它能抓出框架内部的实现疏漏，但**管不了宿主和插件**：宿主把一个 `IPhysics*` 存进自己的成员变量，插件把服务指针塞进未登记的静态变量，都在它的视野之外。后两类是**契约束**，列在 9.3，不在这里假装由机制保证。

### 1.3 服务指针的生命周期不变式

由铁律直接推出：

```text
服务指针的存活期  ⊆  提供方的实例存活区间（⊆ Pod ⊂ 二进制的驻留区间）
```

v2 里中间那层括弧自动成立——提供方随局同死，「服务不跨局」就是全部防线。**v3 的提供方可能在局内被 Eject 提前送走**，这层括弧不再自动成立：补上它的是依赖账本——**Eject 前账本必须证明没有任何活着的实例引用被卸方的服务**（5.6）。宿主侧纪律不变：不跨边界持有服务指针、不缓存（9.3）；库侧的执法点从「局的生死」变成「账的清算」。这条不变式仍是 C++ 里替代 GC 的关键保证。

**推论：宿主提供的服务也随 Pod 销毁。** `ServiceOrigin::kHost`（GPU、引擎桥接这类）的注册入口同样是 `ctx.Provide<T>()`，而 `ctx` 属于某个 Pod。所以即便服务是宿主自己实现的，它也必须**每个 Pod 重新注册一次**。

对只跑一局的游戏本体，这没有区别。对反复建销 Pod 的宿主（编辑器、测试装置），意味着引擎桥接层要跟着每局重建——这通常正是想要的语义（世界本来就每局重建），但它是必须知道的：**没有任何服务的生命周期能长过 Pod。**

### 1.4 PluginHost 是进程内唯一的，且绑定一个线程

**一个进程只有一个 `PluginHost`。** 这不是可选的取舍，而是 9.1 能自洽的**必要条件**：进程级状态的定义（「跟着二进制走」）建在「进程唯一」之上。两个 Host 会有两张二进制表，同一份 DLL 被加载两次、得到两份静态数据——「进程级」当场失去唯一定义。宿主需要并发装配的话，`Pod` 本来就是可多开的（只要都在 Host 那个线程上）。

**`PluginHost` 绑定一个线程。** 宿主创建它时，隐式取**调用创建函数的那个线程**作为 Vase 线程；之后一切 Vase API 必须来自那个线程，Debug 下断言线程 id。

| 为什么是「绑定创建线程」，不是「宿主主线程」 | |
|---|---|
| C++ 没有「主线程」这个语言概念 | 只能靠平台 API 猜，而 Vase 不该碰平台 |
| 引擎的玩法逻辑未必跑在主线程 | UE 跑在 GameThread。写死「主线程」会把引擎适配器坑死 |
| 绑定落在 Host 上，不落在 Pod 上 | Pod 的创建线程可能本来就活不长；Host 是进程级的，它的绑定线程自然长寿 |
| 隐式取而非传 `thread::id` | 传参允许宿主传一个既非当前、也不属于自己的 id，错误会推迟到第一次使用才爆。隐式取的话「绑定的线程」与「创建的线程」永远一致，**创建那一刻就能验** |

宿主若选了个短命线程来创建 Host，那是它自己的设计错误——**第一次调用 API 就会断言失败，是响的**，不会拖到某个随机时刻以更难查的形式爆出来。

**计数的线程安全由此免费获得。** 9.2 要求「计数始终维护」，而单线程契约让这些计数器不需要原子、不需要锁——这是 1.2 到 9.2 之间一条隐性的依赖，写在这里以免日后有人为了「支持多线程」而先拆掉这条契约。

## 2. 核心对象模型

### 2.1 概念集

```text
Pod ──────── Context ───┬── ServiceRegistry
                        ├── EventBus
                        └── EffectScope（每个插件一个）

PluginHost ────────────── 插件二进制表、进程级状态、依赖账本、诊断
PluginCatalog ─────────── 清单表、依赖图、加载计划
```

| 概念 | 职责 |
|---|---|
| **Pod** | 一次运行的边界。创建时装配，销毁时归零；局内叶插件凭账进出（5.6） |
| **Context** | Pod 内的服务访问入口；每个插件拿到的是自己的子 Context |
| **Plugin** | 一个插件实例。描述自身、声明依赖、注册能力、拥有一个 EffectScope |
| **Service** | 能力单元。由插件或宿主提供，经 Context 解析 |
| **Event** | 插件间的解耦通信。两种派发模式（见 6.4） |
| **Effect** | 副作用的统一表示。**唯一**的注册产物形态 |
| **EffectScope** | Effect 的归属容器。随插件销毁而回收，逆序、幂等 |

**关于 Capability**：早期文档把「平台能力」（GPU / Vulkan / Gamepad）单列为 Capability，与 Service 并列。本文取消这个概念——它们在机制上没有任何区别，唯一差别是**谁提供**。GPU 完全可以是一个由宿主提供的 Service。因此它被降为 Service 的一个属性：

```cpp
enum class ServiceOrigin
{
    kPlugin,    // 由某个插件提供
    kHost,      // 由宿主直接注册（平台能力、引擎桥接）
};
```

保留两个注册表、两套查找路径、一整节文档，只为了表达「谁提供的」，不划算。

### 2.2 关系

```text
Pod
   │
   ├──► PluginHost 的加载计划
   │
   ▼
Context（根）
   │
   ├── ServiceRegistry ◄──── Provide<IFoo>()  ──┐
   ├── EventBus         ◄──── On<Event>()     ──┤
   │                                            │
   │                                    全部返回 EffectHandle
   ▼                                            │
Plugin 树（每个插件一个子 Context）              │
   │                                            │
   └──► EffectScope ◄───────────────────────────┘
             │
             └──► 插件销毁时逆序回收全部
```

### 2.3 Context 的边界

`Context` 的能力边界必须明确，否则读者会期望不存在的功能：

1. **不做惰性属性解析。** C++ 没有 `Proxy`，服务必须显式取：`ctx.Get<IPhysics>()`。取不到是显式的运行期错误，不是「读到一个 undefined 属性」。
2. **不做稳态运行期的服务自动重载。** 装配完成之后的稳态运行期里，服务不会消失，因此不存在「依赖方跟随重载」的场景。v3 的局内 Eject **没有**打开这个缺口：被卸者必须无人依赖（5.6 档 ①），所以对任何还活着的服务视图而言，稳态依旧无消失。**注意这个限定词**——装配期（`OnLoad` + `OnStart`）内部服务仍可能消失，见 5.5 的级联拆除。这条限定是刻意的：把它放宽成「服务永不消失」会让 5.5 那一节失去依据。
3. **不做隔离域。** 一次 Pod 一个服务集合。没有可沿作用域覆盖的配置。
4. **有意不支持同名服务多实例。** 一个服务标识在一个 Pod 内只能有一个实现（6.3 的求解规则会拒绝重复）。需要「同时存在两个物理世界」这类需求的，应当由**服务自身的**方法签名承载（`GetPhysics(worldId)`），而不是由注册表承载。**这是设计选择，不是缺失**——一旦支持多实例，就必然要引入沿作用域查找与遮蔽，而那正是第 3 条否掉的东西。

关于**查找语义**：服务注册表是 Pod 一份**扁平**的表，子 `Context` **不是**查找链上的一环。子 Context 存在的理由只有两个——记录 `Effect` 的归属、在诊断时说出「谁注册的」。查表不沿 Context 上溯。

这四条是**刻意的设计取舍，不是尚未实现的功能**——理由见[附录 A](#附录-a与-cordis-的对应与取舍)。

### 2.4 事件与服务的标识方式一致

事件和服务面对**完全相同**的跨 DLL 标识问题，所以用**同一套解法**：`EventId = 名字 + 整数主版本`，与 6.1 的服务标识同构。

```cpp
struct DamageEvent
{
    static constexpr std::string_view kName    = "Vase.Combat.DamageEvent";
    static constexpr uint32_t         kVersion = 1;

    EntityId Target;
    float    Amount;
};
```

`ctx.On<DamageEvent>(...)` 通过 `E::kName` / `E::kVersion` 查表，并用 `static_assert` 校验声明完整。

**如果事件按 C++ 类型标识，6.1 整节的论证对事件就全部失效**——同一个坑（`type_index` 跨 DLL 不稳定）要踩两遍。这里没有第二条路可走。

**事件的生命周期契约**（0.3 第 6 条的具体化）：**派发是同步的；handler 不得保存事件对象的引用，也不得保存其中任何视图。** `ctx.Emit(WorldLoadedEvent{ ... })` 传的通常是个临时对象，派发返回后即失效。

## 3. 插件

一个插件由三部分构成：**C++ 侧的类**、**由类中声明生成的清单**、**导出的入口符号**。三者中只有第一项需要手写。

> **插件作者只包含一个头文件：`#include <Vase/Plugin.h>`。** 它覆盖宏（`VASE_PLUGIN` / `VASE_CONFIG`）、基类、`Context`、`Result`、`Error`。
>
> `Include/Vase/` 下面按模块分的七个子目录（第 10 节）是**给实现和宿主用的**，不是给插件作者用的。让作者记七个路径，等于每开一个新插件都要抄一遍示例——而这类摩擦会直接变成「大家把 `Context` 的用法抄错」。
>
> 这条同时定义了**什么算公开 API**：`Detail/` 里的东西永远不该出现在那个头里。

### 3.1 C++ 侧：最小形态

```cpp
// ===== 服务接口（提供方与消费方共用同一个头文件）=====
class IDamageSystem
{
public:
    static constexpr std::string_view kName    = "Vase.DamageSystem";
    static constexpr uint32_t         kVersion = 1;

    virtual ~IDamageSystem() = default;
    virtual float ApplyDamage(EntityId target, float amount) = 0;
};

// ===== 插件本体 =====
class CombatPlugin final : public vase::Plugin
{
public:
    vase::Result<void> OnLoad(vase::Context& ctx) override
    {
        ctx.Provide<IDamageSystem>(DamageSystem_);
        ctx.On<DamageEvent>(&CombatPlugin::OnDamage, this);
        return {};
    }

    vase::Result<void> OnStart(vase::Context& ctx) override
    {
        timer_ = ctx.Scheduler().Every(std::chrono::milliseconds(16), [this] { Tick(); });
        return {};   // timer_ 是 EffectHandle：本插件一被回收，定时器自动注销
    }

private:
    void OnDamage(const DamageEvent&);
    void Tick();

    DamageSystem      DamageSystem_;
    vase::EffectHandle timer_;
};

// ===== 元信息：把所有声明收拢到一处；VaseCli scan 从二进制里读出它 =====
// （CombatConfig 与 kProcessStates 的定义分别见 3.2 与 9.1）
VASE_PLUGIN(CombatPlugin)
{
    .Id           = "Vase.Combat",
    .DisplayName  = "战斗系统",
    .Version      = "1.2.0",
    .Requires     = { { "Vase.World", 1 } },
    .Provides     = { { "Vase.DamageSystem", 1 } },
    .Config       = vase::FieldsOf<CombatConfig>,   // ← 3.2 定义的配置元信息
    .ProcessState = kProcessStates,                 // ← 9.1 定义的进程级状态表
};
```

> 例中的 `Scheduler` 是**另一个服务**，由宿主或别的插件提供——Vase 本体不提供任何业务服务（见 0.1 的边界表）。它出现在这里只是为了演示 `OnStart` 里注册的 Effect 会被自动回收。

#### 基类 `vase::Plugin` 只有三个虚函数

```cpp
namespace vase
{

class Plugin
{
public:
    virtual ~Plugin() = default;

    virtual Result<void> OnLoad(Context& ctx) = 0;
    virtual Result<void> OnStart(Context& ctx) { return {}; }
};

} // namespace vase
```

**没有 `GetDescriptor()`。** 描述符是**二进制级**的导出符号（`VasePluginDesc_<类名>()`，见下），不是实例的成员——**一个镜像一份描述符，不是每个实例一份**。把它写成虚函数会诱导读者以为「同一个插件的不同实例可以有不同描述符」，而本设计里不存在这个自由度：一个 Pod 内一个服务标识只有一个实现，一个进程只有一个 `PluginHost`（1.4）。

虚析构必须存在：Vase 通过 `VasePluginDestroy_<类名>()` 销毁实例，而那个函数在插件的镜像内 `delete`——虚析构是这条路径正确的前提。

`OnStart` 有默认空实现（不是所有插件都需要启动动作）；`OnLoad` 是纯虚（每个插件至少要做点什么）。

#### 描述符是唯一入口

一个插件的全部元信息——身份、依赖、提供的能力、配置项、进程级状态——都收拢在上面这一个块里。**那三处声明不是三份独立的声明，而是同一份描述符的三个引用：**

| 描述符里的内容 | 从哪来 | 谁读它 |
|---|---|---|
| **头文件版本：`HeaderVersion`** | **由 Vase 头文件提供，不由插件作者写** | `PluginHost` 加载时**最先**检查 |
| 身份：`Id` / `DisplayName` / `Version` | `VASE_PLUGIN` 直接写 | 清单的身份段、宿主 |
| 依赖与服务：`Requires` / `Provides` | `VASE_PLUGIN` 直接写 | Catalog 求解、加载期校验 |
| 配置项：`Config` | 指向 `VASE_CONFIG` 生成的 `kFields`（3.2） | 清单的 `config` 段、宿主界面 |
| 进程级状态：`ProcessState` | 指向插件声明的 `kProcessStates[]`（9.1） | 加载期登记、诊断 |
| 工厂：`Create` / `Destroy` | 由 `VASE_PLUGIN` 自动生成 | 加载期实例化插件 |

**`HeaderVersion` 是 8.3 那条前提唯一的执行点。** 8.3 把「插件与宿主包含同一份 Vase 头文件」列为纯 C++ 接口的**前提**，但只写前提不写检查，它就只是一句祈使句——用旧头文件编译的插件，vtables 布局、结构体大小、枚举值都可能不同，而 8.2 的「文件可替换」验证对此一无所知。

所以：**头文件里定义一个整数版本，随每次不兼容改动递增；`VASE_PLUGIN` 自动把它写进描述符；`PluginHost` 加载时第一个读它，不匹配就拒绝。** 插件作者不需要知道它的存在。

这个拼装是**显式的**，因为它本来能隐式的话也轮不到我们——cordis 那边 `inject` / `Config` 是挂在插件**值**上的属性，运行时直接读；C++ 没有这件事。`.Config = vase::FieldsOf<CombatConfig>` 这一行就是那个「挂上去」的动作，没有它，配置元信息就只是一份没人认领的静态数据。

**新增一处声明时，必须同时在描述符里引用它**——这是 `VASE_PLUGIN` 不能被省略的原因，也是 3.4 节「清单由描述符生成、描述符由代码生成」这条链的起点。

但这里有一个**已知的静默失败点**，必须写下来：如果作者写了 `VASE_CONFIG` 却忘了在描述符里写 `.Config`——

- 插件照常编译、照常加载、照常跑；
- `ctx.Config<CombatConfig>()` 照常拿到配置（结构体和服务是两回事）；
- 只有**宿主界面上的配置面板凭空消失**。

**加载期的「清单 ↔ 描述符」比对拦不住它**——两边都缺这一段，比对结果是一致的（12 节第 8 条因此不覆盖这种情况）。检测手段目前只有「人看一眼界面」。13 节记了一条结构性修法。

`VASE_PLUGIN(Type)` 展开出三样东西：

1. **工厂函数**——Vase 用它实例化插件。虚表在 DLL 里，宿主不能自己 `new`：

   ```cpp
   vase::Plugin* VasePluginCreate_CombatPlugin()                { return new CombatPlugin(); }
   void          VasePluginDestroy_CombatPlugin(vase::Plugin*)  { /* delete */ }
   ```

2. **唯一命名的描述符符号**——元信息加上函数指针，作为**静态 POD 数据**放在数据段。**符号名由类名派生，不是插件 Id**：

   ```cpp
   extern "C" VASE_EXPORT const vase::PluginDescriptor* VasePluginDesc_CombatPlugin();
   ```

   **为什么不拿 Id 做符号名**：Id 是 `"Vase.Combat"` 这种含点号的字符串，不是合法标识符；而类名（`CombatPlugin`）合法，且在一个镜像里天然唯一。这样作者仍然只写一处（`VASE_PLUGIN(CombatPlugin)`），不必为了符号名把 Id 再抄一遍——3.1 开头说的「只有第一项需要手写」得以保持。

3. **统一入口**——只在「一个库装一个插件」时有意义，因为它只认一个 Id：

   ```cpp
   extern "C" VASE_EXPORT const vase::PluginDescriptor*
   VasePlugin_GetPlugin(const char* id);   // 只认 "Vase.Combat"，其余返回 nullptr
   ```

   **组合库里没有这一项。** N 个插件链进同一个镜像时，N 个同名符号会直接冲突。组合库的入口由 VasePack 生成，见 8.6。

描述符必须是 POD（固定布局、数组加长度、`const char*` 而非 `std::string`），这样 `VaseCli scan` 只要**读数据段**就能拿到全部元信息，**不必执行 DLL 里的任何代码**——连实例化插件都不必。这比「导出一个返回 JSON 的函数」安全得多：扫描一个插件不该执行它的代码。

> 与对照实现的差别：cordis 的插件是一个运行时**值**（函数／类／对象），声明作为属性挂在它身上直接读；UE5 的模块是 `IMPLEMENT_MODULE` 宏加 `IModuleInterface` 虚函数，元信息另写一份 `.uplugin`。C++ 的 DLL 导出是**符号级**的——导出的是函数地址，不是「一个可以直接调用的东西」，更没法把属性挂在函数上。所以 Vase 必须走「导出描述符」这条路。详见[附录 A](#附录-a与-cordis-的对应与取舍)。

### 3.2 配置：宏反射

配置在代码里是**有类型的结构体**（插件直接成员访问，不做字符串查表），同时又要能被宿主反射出来生成界面。C++20 没有原生反射，所以用宏：**字段列表只写一次，展开两次**——一次生成结构体成员，一次生成元信息表。展开由库内部的 `VASE_FOR_EACH` 完成，用户看不见。

```cpp
// ===== 作者写的（唯一一处）=====
VASE_CONFIG(CombatConfig,
    //  类型    字段名                 默认值   元信息
    (float, CriticalMultiplier, 2.0f, vase::Meta{.Label = "暴击倍率", .Min = 1.0f, .Max = 10.0f}),
    (bool,  FriendlyFire,       false, vase::Meta{.Label = "友军伤害"}))
```

每个字段是一个**括号元组**。元组的括号就是保护壳——正因为外面有一层括号兜着，元信息里才可以写原生的 `vase::Meta{.Label = "...", .Min = 1.0f}`，不必为了躲开预处理器的参数切分而套一层再剥掉。

展开成：

```cpp
struct CombatConfig
{
    // ① 成员：类型安全，插件里写 cfg.FriendlyFire
    float CriticalMultiplier = 2.0f;
    bool  FriendlyFire       = false;

    // ② 元信息表：POD、static constexpr；宿主、VaseCli 与装配期读它
    static constexpr std::array<vase::FieldInfo, 2> kFields = {{
        { "CriticalMultiplier", vase::TypeTag<float>{}, vase::Value{2.0f},
          .Min = 1.0f, .Max = 10.0f, .Label = "暴击倍率",
          .Apply = vase::ApplyTo<&CombatConfig::CriticalMultiplier> },
        { "FriendlyFire", vase::TypeTag<bool>{}, vase::Value{false},
          .Label = "友军伤害",
          .Apply = vase::ApplyTo<&CombatConfig::FriendlyFire> },
    }};
};
```

两侧用法：

```cpp
// 插件里：编译期检查，无字符串
const CombatConfig& cfg = ctx.Config<CombatConfig>();
if (cfg.FriendlyFire) { /* ... */ }

// 宿主侧：遍历 kFields 生成界面，类型、默认值、范围、显示名齐备
```

#### 配置在运行时的表示：`ConfigBlob`

上面那张 `kFields` 表还有一个**此前没写出来的职责**：它是「无类型的配置数据」与「有类型的配置结构体」之间唯一的桥梁。没有它，第 4 节的 Preset 覆盖（JSON）就没有任何路径能抵达 `CombatConfig`。

中间那层数据叫 **`ConfigBlob`**：

```cpp
// 扁平的「字段名 → 值」映射。纯数据，无类型，不依赖 JSON。
struct ConfigBlob
{
    std::vector<std::pair<const char*, vase::Value>> Fields;
};
```

**合并全在 `ConfigBlob` 层做**——清单默认值、Preset 覆盖、本局临时覆盖（4.3 的三层）都是 `ConfigBlob`，4.2 的「逐字段浅合并」就是在它们之间做。理由：这一层无类型、无 JSON、无插件代码，**合并逻辑因此可以被单元测试穷举**。

写进结构体由 `FieldInfo::Apply` 负责——`vase::ApplyTo<&CombatConfig::FriendlyFire>` 展开出一个 `void(*)(void*, const Value&)` 的函数指针（由 `VASE_CONFIG` 自动生成，作者看不见）。装配期遍历 `kFields`，对每个字段按名字从 blob 取值、调 `Apply` 写入。

于是整条链路是：

```text
Preset (JSON) ──[Catalog 解析]──► ConfigBlob ──[浅合并]──► ConfigBlob ──[kFields 的 Apply]──► CombatConfig
                                  ↑
                            清单默认值也在这一层
```

**JSON 只出现在最左边那一处**，其余全是不依赖任何第三方库的纯数据。这也是 4.1 说得出口「宿主保存为 Preset」的原因——反向转换同样只发生在那个边界上。

代价有四条，两条在库内部，两条由插件作者承担：

| 代价 | 谁承担 | 说明 |
|---|---|---|
| 需要一个计数宏与 `VASE_FOR_EACH` | 库实现 | 标准技巧，写一次就不用再管 |
| 元组展开机制 | 库实现 | 同上 |
| **IDE 支持打折** | **插件作者** | 宏展开出来的成员，跳转、补全、重命名可能不认。UE 的 `UPROPERTY` 有同样问题——这是 C++ 宏反射的通用代价。**若实际使用中不可忍受，附录 B.2 记了一条逃生口** |
| 每个字段多一对括号 | 插件作者 | 元组本身是保护壳，代价很小 |

这套设计的真正收益在这里：**「结构体成员」与「元信息表」来自同一次宏展开，一致性是构造出来的，不是靠测试或纪律保证的。** 手写 schema 表之所以不可接受（就是你否掉的那个方案），根因是它把同一个事实写了两遍，而两遍总会漂移——加了一个字段忘了加元信息，宿主界面上就少一个开关，没有任何东西会报错。

**`FieldInfo` 的布局是对外契约，宏不是。** C++26 的原生反射（P2996）会把这个语法换掉——届时的形态是成员注解：

```cpp
struct CombatConfig
{
    [[=vase::Label("暴击倍率"), =vase::Range(1.0f, 10.0f)]]
    float CriticalMultiplier = 2.0f;
};
```

**没有宏、也没有字段列表**，`consteval` 直接读注解。所以不管现在选哪种宏形态，届时用户代码都要改写——别把「未来兼容」当作选型依据。

真正跨版本不变的是 `kFields` 这张表：下游（宿主界面、`VaseCli`）读的始终是它，宏只是它**当前**的生产者。把 `FieldInfo` 当接口对待，生产者可以换三次。

（同样地，`VASE_PLUGIN` 的展开物也是契约：工厂函数、描述符布局、导出符号名。三者任一变化，都会破坏「先扫描后加载」这条流程。）

### 3.3 清单：`.plugin.json`

清单与二进制并排放置在**宿主的插件目录**里（这个目录属于宿主，不属于 Vase 仓库）：

```text
<宿主的插件目录>/
├── VaseCombat.dll
└── VaseCombat.plugin.json      ← stem 与 DLL stem 一致
```

命名遵循 `<stem>.<kind>.json` 家族，与 Preset 的 `<Name>.preset.json` 保持一致，便于统一 glob。

清单的字段如下。注意它们**全部由 3.1 / 3.2 的 C++ 声明生成**，没有人手写这份 JSON：

```jsonc
// VaseCombat.plugin.json
{
    "schemaVersion": 1,

    "id": "Vase.Combat",
    "displayName": "战斗系统",
    "version": "1.2.0",

    "binary": "VaseCombat",          // DLL stem；缺省时取文件 stem
    "enabledByDefault": true,        // Preset 未提及时是否参与

    // 我依赖的服务。缺任何一个 → 本局跳过该插件
    "requires": [
        { "service": "Vase.World", "version": 1 }
    ],

    // 可选依赖。缺失不导致跳过，插件需要自行处理「拿到 null」
    "optionalRequires": [
        { "service": "Vase.Audio", "version": 1 }
    ],

    // 我提供的服务
    "provides": [
        { "service": "Vase.DamageSystem", "version": 1 },
        { "service": "Vase.AttributeSystem", "version": 1 }
    ],

    // 配置项。宿主据此自动生成界面
    "config": [
        {
            "key": "criticalMultiplier",
            "type": "float",
            "default": 2.0,
            "min": 1.0,
            "max": 10.0,
            "displayName": "暴击倍率"
        },
        {
            "key": "friendlyFire",
            "type": "bool",
            "default": false,
            "displayName": "友军伤害"
        }
    ]
}
```

`config` 的 `type` 取值集合见 13.2：`bool` / `int32` / `int64` / `float` / `double` / `string` / `enum`。**不支持嵌套对象与数组**——理由见 4.2。

**清单里只放 Vase 认识的东西。** 「图标」「分类」「作者」这类字段不在这里——它们是宿主的概念，不是插件运行时的概念。宿主若需要，自己维护一份旁路元数据（例如 `<宿主插件目录>/<id>.host.json`），按 `id` 关联即可。这条界限要守住：一旦允许任意字段混进清单，「清单全部由代码生成」这个性质就没了，scan 就从「覆盖式生成」退化成「合并式更新」，而合并语义要处理冲突、删除、人工修改，复杂度陡增。

**清单里有两个版本号，含义完全不同，不要混：**

| 字段 | 管什么 | 不匹配时 |
|---|---|---|
| `version` | **插件自己的版本**，纯展示 | **不参与任何判断** |
| `schemaVersion` | **清单 JSON 格式的版本** | 主版本不同即拒绝加载 |

关于 `version`：文档定义了它、生成了它、展示了它，**没有任何一处消费它**——依赖是服务级的（`requires` 带的是**服务**版本，见 6.1）。这是有意的：**一旦插件版本参与依赖判断，就和服务版本形成两套并行的兼容规则**，而 6.3 的「一服务一实现」已经把兼容性完全押在服务版本上了。它只出现在宿主界面和 `VaseCli list` 里。

好处是**插件升级不需要求解逻辑参与**——改个字符串、重新编译、扫描，就完事了。

关于 `schemaVersion`：与 6.1 的服务版本**同一条规律**——主版本不同即拒绝，次要差异（新增可选字段）容忍。而且**扫描期与加载期必须用同一规则**：`VaseCli scan` 和 `PluginHost` 若各自判断，就会出现「工具说没问题、运行时拒绝」的分歧，而 3.4 的整条流程恰恰建在「两边结论一致」上。

### 3.4 清单的权威性与生成流程

清单有**两个副本**，必须一致；权威在二进制里。

```text
插件作者写代码
    │  声明：服务标识、依赖、配置项（作为编译期常量与静态成员）
    ▼
编译出 VaseCombat.dll
    │
    │  VaseCli scan（构建期，一次性）
    │  · 加载 DLL
    │  · 读出导出的描述符
    │  · 生成 VaseCombat.plugin.json
    │  · 立即卸载
    ▼
VaseCombat.plugin.json          ← 外部副本，工具与宿主读它
    │
    │  加载期加载 DLL
    │  · 先读 HeaderVersion —— 不匹配即拒绝（8.3 的前提在此兑现）
    │  · 读出描述符
    │  · 与 .plugin.json 逐字段比对（含 schemaVersion）
    │  · 不一致 → 拒绝加载并报告
    ▼
Pod
```

三个时点各有职责：

| 时点 | 谁 | 是否加载二进制 | 目的 |
|---|---|---|---|
| 构建期 | `VaseCli scan` | **是**（一次性，随即卸载） | 从代码生成清单，杜绝手写漂移 |
| 枚举期 | 编辑器 / `VaseCli` / Catalog | **否** | 列出插件、求解依赖、校验 Preset |
| 加载期 | `PluginHost` | 是 | 比对清单与代码，拒绝漂移 |

「枚举期不加载二进制」是这套流程存在的理由：宿主画一个插件列表不该冒加载 DLL 的风险。

**枚举期还有一件事：插件 `Id` 查重。** `PluginCatalog` 建立清单表时，两个 DLL 声明同一个 `Id` 必须**硬报错**，不是 warn。理由：`Id` 是 Preset 的 key（4.1），重复会让「这条覆盖到底改了谁」变得不确定——**静默错误的温床**。服务重名在求解期报错（6.3），插件 Id 重名应该更早，在扫描期就拦住。

**清单与二进制不符时，优先信二进制。** 加载期的比对只做一件事：确认两者一致，不一致就拒绝。它**不尝试修复**、也不用某一方去覆盖另一方——「两个副本 + 一次比对」的模型之所以简单，正是因为分歧只有「拒绝」这一种处置。

## 4. Preset（插件集）

**Preset** 描述「哪些插件参与、各自配置如何」。它有名字、落盘、可切换。

### 4.1 增量语义

Preset **只记录偏离默认的部分**，不是全量列表。

```jsonc
// Presets/Client.preset.json
{
    "schemaVersion": 1,
    "displayName": "客户端",

    "overrides": {
        // 没提到的插件 = 按清单的 enabledByDefault 与 config 默认值处理
        "Vase.Combat":       { "config": { "friendlyFire": true } },
        "Vase.Server.Admin": { "enabled": false }
    }
}
```

选增量而非全量，理由有三，第一条最重要：

1. **新写的插件不需要改任何 Preset 就能跑。** 把插件放进宿主的插件目录、起一次 Pod，它自动参与。全量列表会让「我明明加了插件怎么没生效」变成日常困惑。
2. 文件短、diff 干净、进版本库不吵人。
3. 它与「本局临时覆盖」是同一种数据结构——区别只在落不落盘。

**谁解析 Preset：`PluginCatalog`，不是 `Pod`。** 理由：Catalog 本来就是「元数据、工具、宿主共用」的那一层，是给 `VaseCli` 和编辑器用的；`Pod` 不碰文件系统、不碰 JSON。**JSON 依赖因此只落在最上面那一层**，核心库不带它。这也解释了 5.1 的 `Solve` 为什么能同时接受「一个路径」和「一个已解析的 Preset 值」——两种输入都由 Catalog 消化。

**引用了不存在的插件 `Id` 时：不报错，记 warn**，并在 `VaseCli validate` 与宿主的诊断报告里列出来。理由：Preset 是增量的，插件被临时删掉、换了名字、或还没构建出来都是常态；报错会让「删掉一个插件」变成「必须同步改所有 Preset」——**这条摩擦会直接导致没人敢删插件**，而脏 Preset 比脏代码更难发现。

### 4.2 配置合并规则

**逐字段浅合并，嵌套对象视为不可分割的整体值。合并发生在 `ConfigBlob` 层**（3.2）——纯数据、无类型、不依赖 JSON、不触碰插件代码，因此**合并逻辑可以被单元测试穷举**。

选浅合并而非深合并，是因为深合并有两个无解问题：数组怎么合（追加？替换？），以及如何表达「清空一个数组」。对 C++ 而言浅合并也更自然——配置就是一个结构体，覆盖就是「哪些顶层字段用 Preset 的值」。

顺带：**这一条也把「配置支持嵌套对象与数组」这个问题一起答了**——不支持。浅合并的语义和嵌套结构不兼容，而引入递归合并要为它定义数组语义、为空语义、类型冲突语义，收益却只是少数插件面板好看一点。

### 4.3 三层应用

```text
清单里的默认值（代码）
        ▲ 被覆盖
Preset（落盘的、命名的覆盖集）
        ▲ 被覆盖
本局临时覆盖（内存的、匿名的覆盖集）
```

三层应用，两种数据。宿主可以随时把内存里的覆盖集存成新 Preset——「临时调整」和「保存为 Preset」之间没有转换代码。

### 4.4 静态求解

因为清单是外部可见的，Catalog **不加载任何二进制**就能算出：

- 最终参与本局的插件集合
- 每个插件的最终配置（默认值 + Preset 覆盖合并后的结果，即 3.2 的 `ConfigBlob`）
- 哪些插件会因**静态原因**被跳过，以及原因是什么

**求解器是纯函数**：`PluginCatalog::Solve(const LoadRequest&) -> Result<LoadPlan>`。它是**公开 API**，`VaseCli` 和编辑器直接调它预览；`CreatePod` 接受的是 `LoadPlan` 而不是 `LoadRequest`——所以「求解」和「装配」是**同一次计算**，不是两次各算一遍。没有第二次求解，就没有漂移的可能。

**Catalog 是有状态的，但状态只通过显式 `Refresh()` 改变。**

```cpp
void PluginCatalog::Refresh();   // 重扫插件目录、重建清单表、查重 Id
```

`Solve` 用**当前快照**。**不做自动文件监视**——那是宿主的活儿（编辑器自己会 watch 目录）。理由不是省事，而是**时机可控**：编辑器在「构建完成」后调一次 `Refresh`，语义明确；自动监视则会让 `Solve` 的结果随文件系统抖动而变，而 4.4 与 5.1 的整个「同一次计算」论证，前提就是同一个快照产出的计划不会中途变脸。**批装配吃快照；v3 的 `AdoptPlugin` 是单点操作，例外——它就地重读目标插件的清单**（等价于局部 `RefreshPlugin`），不吃可能过期的快照。理由：11.2 的热重载流程里 scan 刚重生成清单，「Adopt 必须见到刚 scan 的那份」是 3.4 一致性链的一环，交给整目录 Refresh 会让每次热重载都重扫全库。

这个能力要能被宿主实时呈现出来——典型形态是编辑器勾选框旁边的一行提示：「取消勾选 Physics 将导致 Combat、Vfx 被跳过」。

> **要求（已收窄，注意限定词）**：静态求解保证的是——**在没有运行时失败的前提下**，实际参与集合与预测一致。
>
> 这不是废话，它是一条**可证伪**的承诺（见 12 节第 9 条）。收窄的原因在 5.5：如果有插件在 `OnLoad` 或 `OnStart` 里崩了，它的下游会被级联跳过，而**这件事在求解期不可能被知道**——那需要执行代码。一个「不加载任何二进制」的求解器，不可能预测「`Vase.Physics` 会在 `OnLoad` 里抛异常」。

因此跳过必须分成两类，宿主界面也要**分开呈现**：

| | 何时产生 | 能否预测 |
|---|---|---|
| **静态跳过** | 求解期：被 Preset 禁用、依赖图不满足（含版本不匹配） | **能**，编辑器实时显示 |
| **运行时跳过** | 装配期：上游插件 `OnLoad` / `OnStart` 失败，级联下来 | **不能**，只能在事后报告 |

把两者混成一个「被跳过了」，就会让「我明明看到它会跑」变成日常纠纷。

## 5. 加载计划与生命周期

### 5.1 输入与输出

```cpp
// ===== 求解：纯函数，公开 API。VaseCli、编辑器、宿主都直接调它 =====
struct LoadRequest
{
    std::filesystem::path           PluginDirectory;
    std::optional<Preset>           Preset;
    std::span<const PluginOverride> PodOverrides;   // 本局临时覆盖
};

// Catalog 求解出的计划。注意 ResolvedConfig 是 ConfigBlob（见 3.2），
// 默认值已经并进去了，但还没有写进任何有类型的结构体。
struct LoadPlan
{
    struct Entry
    {
        PluginId     Id;
        LoadDecision Decision;        // kLoad | kSkip
        SkipReason   Reason;          // Decision == kSkip 时有效
        ConfigBlob   ResolvedConfig;
    };

    std::vector<Entry> Ordered;       // Decision == kLoad 的，已按拓扑序排好
};

Result<LoadPlan> PluginCatalog::Solve(const LoadRequest&);

// ===== 装配：接受已算好的计划，不再重新求解 =====
struct PodOptions
{
    bool Strict = false;              // 任一插件失败即整局失败（5.5）
};

Result<PodHandle> PluginHost::CreatePod(const LoadPlan&, PodOptions);
PodReport         PluginHost::DestroyPod(PodHandle);

// ===== v3：局内进出（机制与执法见 5.6）=====
Result<AdoptReport> PluginHost::AdoptPlugin(PodHandle, const PluginId&);
// AdoptReport：载明档三身份特征验新结果（8.2，含驻留复用分支）与导入表执法结论（8.7）
Result<EjectReport> PluginHost::EjectPlugin(PodHandle, const PluginId&);
// EjectReport：被拒时点名每个消费者；成功时载明三档证据与重置了哪些进程级状态（9.1）
```

求解失败（循环依赖、同一服务被两个插件提供、清单损坏、插件 `Id` 重复）返回错误，不产生计划。

**注意两个签名的不对称：`CreatePod` 可能失败，`DestroyPod` 永不失败。**

`CreatePod` 只有三种失败情形：`LoadPlan` 与磁盘实际不符、插件二进制加载不了（`HeaderVersion` 不匹配等）、严格模式下有插件失败。

`DestroyPod` 返回的是报告而不是 `Result`——**拆除路径半途放弃会让状态比泄漏更烂**（半个 Pod 还活着），而 5.5 的「失败不致命」也是同一条原则。这是「干净关停」在 API 层面的体现。

**`LoadPlan` 里只有静态跳过**（4.4）。运行时跳过是装配期才知道的，它出现在 `PodReport` 里，不在计划里——计划是求解的产物，而求解不执行代码。

**`PodHandle` 是不透明句柄**（索引 + 代际），不是裸指针。取用期通过 `PluginHost::Resolve(PodHandle) -> Pod*` 拿到引用，失效时返回 `nullptr`——「句柄失效」在这套设计里不是错误，是预期内的正常情况。**宿主不要缓存 `Pod*`**：裸指针会诱导缓存，而缓存 Pod 引用正好踩 1.3 的不变式；代际句柄在 Pod 销毁后再用会被检出来。

### 5.2 Plugin 状态机

```text
Discovered   清单已知，尚未参与
     │
     │  ① 求解（纯数据，不执行任何代码）
     ├──► Skipped[静态] ──── 被 Preset 禁用 / 依赖不满足（含版本不匹配）
     ▼
  Loading    加载二进制、执行 OnLoad
     │
     ├──► Failed ──┬── 立即回收本插件的 EffectScope
     │             └── 下游级联为 Skipped[运行时]（它们还没开始）
     ▼
  Loaded     服务已注册
     │
     │  ② 全部进入 Loaded 后统一启动
     ▼
  Started    运行中
     │
     ├──► Failed ──┬── 立即回收本插件的 EffectScope
     │             └── 下游递归拆除（它们已经在跑了，见下）
     │
     │  ③ 关停：逆拓扑序回收 EffectScope
     ▼
 Stopping
     │
     ▼
 Unloaded
```

**`Failed` 不是真正的终态——它保留的是记录，不是实例。**

`Failed` 时**立刻回收本插件的 `EffectScope`**：`OnLoad` 里注册到一半的服务与订阅必须当场拆干净，否则就是泄漏。状态机里 `Failed --本局销毁--> Unloaded` 这条边存在，只是那时回收的是一个已经空了的 Scope。

保留下来的是**一份不含 `Effect` 的轻量诊断记录**（`Id` + 失败阶段 + `Error`）。它**不算「插件实例」**，所以 9.2 的「插件实例数 → 0」断言仍然成立。**「保留实例以便诊断」这句话要改读成「保留记录以便诊断」**——保留的从来不是实例。

**`OnStart` 失败的下游处理，是本设计里最容易写错的一条。**

`Loading` 阶段失败时，拓扑序保证下游**还没开始**，它们变 `Skipped` 顺理成章。但 `Started` 阶段失败时，**所有插件的 `OnLoad` 都已经跑完**——下游已经 `Loaded`、可能已经 `Started`、已经注册了服务、订阅了事件。**它们没法「变为 `Skipped`」，它们已经在跑了。**

处理方式是**递归拆除**：把下游及其下游按逆拓扑序回收 `EffectScope`，退回 `Skipped[运行时]`。这个过程可能连锁——被拆掉的插件所提供的服务一并注销，可能触发再下一级的下游也被拆。

**这是本设计里服务唯一会消失的时刻，而且是刻意的。** 2.3 第 2 条那句「不做**稳态运行期**的服务自动重载」，限定词正是为此而加：装配期（`Load` + `Start`）内部服务仍可能消失。

**它不是 cordis 的 epoch 机制**——它只在装配期发生一次，不会在稳态中反复触发，所以不需要指纹、不需要惯性、不需要恢复路径。它只是把「依赖者不参与」这一条规则，从 `Loading` 延伸到了 `Start`。这也说明我们砍掉 `epoch` 的那个理由（「服务在 Pod 存活期内不会消失」）**原本就写得宽了**，现在收窄成准确的表述。

### 5.3 加载的两阶段

```text
阶段 0            宿主注册回调（可选，`CreatePod` 传入）
                    · 宿主的服务在这里注册，挂 Pod 根 EffectScope
                    · 此时还没有任何插件 Load —— 宿主服务天然先于插件可见
                       ↓
阶段 1（拓扑序）   OnLoad(Context&)
                    · 注册服务、订阅事件
                    · 可以安全使用「自己声明的依赖」所提供的服务
                      （拓扑序保证它们已 Load）
                    · 但不得假设「非依赖」插件已就绪，也不得开始活动
                       ↓
阶段 2（拓扑序）   OnStart(Context&)
                    · 所有插件的 OnLoad 全部完成后统一开始
                    · 此时全部服务就绪，可以安全地使用任意服务
```

**阶段 1 的意义：把「服务注册」与「开始活动」解耦。** 如果只有一个阶段，插件 A 启动时发出的事件可能早于插件 B 完成订阅——而 B 在拓扑序上排在 A 之后是完全合法的。两阶段消除了这类时序竞态。

**阶段 0 的意义：宿主服务不需要伪装成插件服务。** 没有这个钩子，宿主只能让某个插件替它注册自己的服务——那会让「谁提供的」这个本该清晰的属性变得含糊，也会让宿主服务的回收归属无处安放。

**三个阶段都必须在 `PluginHost` 绑定的那个线程上执行**（1.4）。这不是建议：9.2 的计数、1.2 的铁律、诊断报告的一致性，全都默认这段控制流是单线程的。

> **关于 `Effect` 注册的纪律，准确的表述是「只允许发生在 Host 绑定的线程上」，不是「只允许在 `OnLoad` / `OnStart` 里」。**
>
> 装配期（阶段 0–2）自动满足这条；运行期通过 `ctx.CreateScope()` 创建的子作用域（7.5），只要也在同一个线程上创建，同样满足。**限制的是线程，不是阶段**——写成「阶段」会把一条本来可用的能力（运行时按需订阅）误伤掉。

### 5.4 关停：不需要 OnStop 钩子

关停时**逆拓扑序**回收各插件的 EffectScope。回收顺序 = 注册顺序的逆序。

因此不需要 `OnStop` 钩子：

```text
OnLoad 里注册的 Effect     ──┐
OnStart 里注册的 Effect    ──┤ 注册更晚
                            │
                            ▼ 回收更早
```

一个在 `OnStart` 里启动线程的插件，只需把「停止线程」也注册为 Effect。它注册得比服务注册更晚，于是回收得更早——线程先停，服务后注销，正好是正确的顺序。

**这个顺序保证是「一切皆 Effect」换来的。** 手写 `OnStop` 反而给了写错的余地。

**但它有一个前提：构造函数不是注册副作用的合法位置。** 上面的论证依赖「`OnStart` 里注册的 Effect 比 `OnLoad` 里的晚」。如果插件在**构造函数**里起了线程并注册了对应的停止 Effect，那个 Effect 会比 `OnLoad` 里的服务注册更早——回收更晚，线程就会在服务已注销之后继续跑。

所以约定：**插件构造函数只做初始化，不注册副作用、不启动活动。** 那时还没有 `Context` 可用，本来也注册不了——这条与其说是纪律，不如说是接口形状的自然结果，但需要在文档里写明，否则它会以「某个插件构造函数里 `std::thread` 一跑就崩」的形式重新出现。

### 5.5 部分失败语义

默认**宽容**：单个插件失败 → 标记 `Failed` → 依赖它（含间接依赖）的插件被级联处理 → 其余照常运行，整局不崩。

**两个阶段失败的后果完全不同，这是本节的核心：**

| 失败发生在 | 下游当时的状态 | 处置 |
|---|---|---|
| `Loading`（`OnLoad` 里） | **还没开始**——拓扑序保证 | 直接变 `Skipped[运行时]` |
| `Started`（`OnStart` 里） | **已经在跑了**——它们早已 `Loaded` | **递归拆除**：逆拓扑序回收它们的 `EffectScope`，退回 `Skipped[运行时]`；可能连锁 |

两种情形下，失败插件**自己的** `EffectScope` 都当场回收（5.2）。

**为什么 `Started` 失败不能照抄 `Loading` 的处置**：`OnStart` 阶段所有插件的 `OnLoad` 都已经跑完了，下游已经注册了服务、订阅了事件。它们**没有「变为 `Skipped`」这个选项**——已经在跑的东西只能被拆掉。这就是「装配期内部服务仍会消失」的全部来源（2.3 第 2 条的限定词、5.2 的递归拆除）。

宿主可通过 `PodOptions.Strict = true` 要求**严格**模式：任一插件失败则整局装配失败——`CreatePod` 返回错误，已经建立的半个 Pod 被销毁。**严格模式是装配策略，不是求解输入也不是求解结果**，所以它在 `PodOptions` 里，不在 `LoadPlan` 里。

无论哪种模式，失败清单都要能被宿主读出来并展示，且**必须区分静态跳过与运行时跳过**（4.4）——前者可预测、后者不可预测，混在一起会把「我明明看到它会跑」变成日常纠纷。

### 5.6 局内进出：依赖账本与 Adopt / Eject（v3）

0.2 的 v3 版允许插件在局内随时进出。这句话成立的前提，是「无人依赖」必须是一个**可证伪的断言**——承重机制就是依赖账本。

**账本。** **插件实例**每完成一次服务解析（`Get` / `TryGet`，6.2）落一条边 `(消费方实例 → 提供方实例)`。账本由 `PluginHost` 进程级持有，边带 Pod 归属，`DestroyPod` 时整批清零——于是 9.2 的断言清单多一项免费的：活集合 → 空。**宿主的解析不落边**：宿主没有可供执法的声明清单（「凭声明」对根 Context 无定义），而落了解不开的边会让任何被主循环碰过的插件永远不可热卸——宿主的防线就是 9.3 那条「每次现取、不缓存」。**两条规则互相锁死：**

1. **解析必须凭声明。** `ctx.Get<S>()` 只允许发生在 P 已声明依赖 S 的提供方之上（求解期就决定了谁能拿谁）；未声明的解析走 6.2 的「编程错误」路径，当场被拒。**这条堵住账本最大的洞——隐藏边。**
2. **边随解析建立、随实例销毁消失。** 提供方被卸前，账上只要还挂着一条边，卸载即被拒绝。

粗粒度是刻意的：**哪怕消费方只是「调用一次就丢引用」，声明边照样拦 Eject**。细化（瞬态解析自动过期）是复杂度的黑洞，档 ① 不需要它。事件订阅**不进账本**——订阅是订阅方的 Effect（出边，由 EffectScope 兜底），不产生「别人依赖我」的反向边。

**进出判定流**（全 `Result<T>`，无异常）：

```text
EjectPlugin(pod, T)                        AdoptPlugin(pod, X)
 ① 账本查边：有人依赖 T？                    ① 就地重读 X 的清单（局部单点 Refresh，
    有 → 拒绝，报告点名每个消费者                      不吃 Catalog 旧快照，见 4.4）
 ② 无 → 销毁 T 的实例（Effect 逆序回收，          ② 二进制已驻留？是 → 复用镜像，但先做档三
    复用 7.x 机器）                                     身份比对——与磁盘不符 → 拒绝，提示
 ③ 卸载二进制 → 三档证据链（8.2）                        「先全部 Eject 再试」；否 → 加载 +
 ④ 账本与活集合摘除 T                                   HeaderVersion / 清单校验（v2 全套保留）
                                                   ③ X 声明的每条依赖都能绑定到活集合？
                                                        不齐 → 整体拒绝，报告缺哪条
                                                   ④ X 装配进当前 Pod，其出边落账
                                                        （①-④ 任一步失败 → X 干净退出，无人受累）
```

**四条规则**：

| # | 规则 | 理由 |
|---|---|---|
| ① | **入局必凭全量声明** | 声明依赖绑不齐活集合即整体拒绝。不带病入局，没有「先挂着等依赖」的中间态 |
| ② | **入局者皆为叶** | 已活插件的声明集不可更改 → X 在被采纳那一刻没有入边。推论：**Adopt 失败零级联**——5.5 的递归拆除机器对 Adopt 路径备而不用 |
| ③ | **离场必为叶** | 以账本反查为准，哪怕一条声明未用的边也拒绝。**没有强制模式**——强制拆边就是级联重启（档 ②），13.4 已明文否决 |
| ④ | **全程串行于 Host 线程** | CreatePod / DestroyPod / Adopt / Eject 都在绑定线程上（1.4）。不存在「Eject 撞上半程 Adopt」的交叠态，状态机不需要并发守卫——这是平台难度预算里省得最狠的一条 |

**四条补角（评审定盘，显式化）：** `DestroyPod` 时 Adopted 节点**没有特殊位置**——出边足以让它在活集合的逆拓扑序里领到自己的拆位，与批装载节点同一台机器；`Failed` 状态的插件**可以被 Eject**（拆的是记录与驻留镜像，无实例、必无入边，报告注明）；**Adopt 不改 Preset**——X 留在插件目录里（`enabledByDefault`）下一局就会被自然编入，「临时试试即弃」是宿主的目录管理问题（放临时目录去 Adopt），Vase 不设 `temporary` 标志；Adopted 插件的配置走**同一套三层合并**（清单默认 + Preset + 本局临时，4.3）——热插件没有自己的配置通道。

**两个明确的不管**（防过度承诺）：宿主的解析不落边，其缓存指针账本更看不见——插件侧靠「凭声明」执法，宿主侧只有 9.3 的纪律，这是不对称的**设计决定**而非缺口；经由进程级状态中转的「语义依赖」图上同样不可见——9.1 的追加硬契约 + `EjectReport` 提示面兜底。

**本节没有引入 epoch。** 「依赖集变了没」不做指纹判定，只有「进出那一刻账上有没有边」这一个判定；服务消失之后不存在「依赖方跟随重载」，因为跟随者压根不被允许存在。与 cordis 的机制对照见附录 A.2。

## 6. 服务与依赖解析

### 6.1 服务标识

服务用**编译期常量名字 + 整数主版本**标识。不使用 `std::type_index`——它跨 DLL 的稳定性依赖编译器实现细节，而字符串常量是稳定的。

```cpp
// Vase/Service/Service.h

class IDamageSystem
{
public:
    static constexpr std::string_view kName    = "Vase.DamageSystem";
    static constexpr uint32_t         kVersion = 1;

    virtual ~IDamageSystem() = default;

    virtual float ApplyDamage(EntityId target, float amount) = 0;
};
```

接口上**不声明** `ServiceOrigin`。同一份接口既可能由插件提供、也可能由宿主提供（见 2.1），把它写死在接口上会自相矛盾。来源是**注册位置**的属性，不是接口的属性：在插件的 Context 里 `Provide` 就是 `kPlugin`，在 Pod 根 Context 里 `Provide` 就是 `kHost`。

`ctx.Get<T>()` 通过 `T::kName` / `T::kVersion` 查表，并用 `static_assert` 在编译期校验接口是否声明了标识，报错信息直接告诉作者缺了什么：

```cpp
// 缺失时给出可操作的编译错误，而不是一堆模板展开
static_assert(HasServiceIdentity<T>,
    "服务接口必须声明 kName 与 kVersion。参见 Vase/Service/Service.h 的示例。");
```

**不用 semver 的理由**：C++ 的 ABI 兼容性推不出 semver 的含义。「主版本不同的服务视为不同的服务；次版本差异只记日志」。用整数比用一个会骗人的字符串诚实。

**命名规范：反向域名前缀，且与插件 `Id` 自洽。**

```text
插件 Id          Vase.Combat
它提供的服务     Vase.Combat.DamageSystem
                 Vase.Combat.AttributeSystem
它发出的事件     Vase.Combat.DamageEvent
```

`VaseCli validate` 检查这条自洽性。

**这不是形式主义。** 6.3 规定了「同一服务被两个插件提供 → 求解失败」，而服务名是一个**全局命名空间**——不定前缀约定，两个团队各自声明 `Physics` 就会撞，且只有撞了才知道。等第三方插件进来再改约定的代价，比现在定一条规矩高得多。

宿主自己提供的服务（`ServiceOrigin::kHost`）用宿主自己的前缀，不占用 Vase 的命名空间。

### 6.2 注册与解析

```cpp
// 注册：借用（插件拥有实例，须活得比注册久，通常是插件成员）
EffectHandle h = ctx.Provide<IDamageSystem>(DamageSystem_);

// 注册：移交（Pod 拥有，随 EffectScope 回收时析构）
EffectHandle h = ctx.Provide<IDamageSystem>(std::make_unique<DamageSystem>());

// 解析：必需
IDamageSystem& damage = ctx.Get<IDamageSystem>();

// 解析：可选（对应清单里的 optionalRequires）
IDamageSystem* maybe = ctx.TryGet<IDamageSystem>();
```

`Get<T>()` 失败时**断言（Debug）/ 立即终止（Release）**，不抛异常。

理由：在清单里声明了 `requires` 的插件，依赖不满足时**根本不会被加载**（见 5.2）——所以 `Get<T>()` 失败只可能是**编程错误**（取了没声明的服务，或违反了加载阶段约定），不是运行期状况。用异常表达编程错误，只会让真正的 bug 被某处的 `catch` 吞掉。错误信息须包含插件 Id、缺失的服务名与版本。

**解析即落账（v3）。** 插件实例每一次成功的解析（`Get` / `TryGet`）都在 `PluginHost` 的依赖账本上记一条边（5.6）；**宿主经根 Context 的解析不落边**（5.6 开头）。未声明的解析本来就是上面那条「编程错误」路径——账本把它从纪律**升格为执法点**：声明是解析的通行证，解析是记账的触发器。

### 6.3 依赖的声明与解析

| 位置 | 作用 |
|---|---|
| 清单 `requires` | 供 Catalog 静态求解（枚举期，不加载二进制） |
| 代码里的声明 | 供编译期检查与加载期比对 |

两处都是必需的，但**权威在代码**，清单由 `VaseCli scan` 从二进制生成（见 3.4），因此不存在手工同步漂移。

解析规则：

- 服务缺失 → 依赖方 `Skipped`，不加载
- **版本不匹配 → 与「服务缺失」同等处理。** 消费方声明 `{ "Vase.World", 1 }`，而在场的只有主版本 2 的实现——按 6.1 的定义「主版本不同即不同服务」，这就是服务缺失，依赖方 `Skipped`。次版本差异不影响解析结果，只在日志里记一条
- 同一服务被两个插件提供 → 求解失败，报错（不静默择一）
- 循环依赖 → 求解失败，报错
- 可选依赖缺失 → 不跳过，`TryGet` 返回 `nullptr`

### 6.4 事件派发

**事件的标识方式与生命周期契约见 2.4**——事件与服务共用同一套标识机制（名字 + 整数主版本），派发是同步的、handler 不得留存事件对象或其视图。本节只讲派发模式。

EventBus 提供两种模式：

| 模式 | 语义 | 用途 |
|---|---|---|
| **Emit** | 同步广播，忽略返回值 | 通知：状态变化、生命周期事件 |
| **Waterfall** | 洋葱模型，每个监听者收到 `Next()`，可决定是否继续、可改写参数 | 可拦截的查询与决策链 |

Waterfall 让插件能**介入并改写**其它插件的行为，这是「插件可组合」超出「监听」的那部分价值。

**不提供 `parallel` / `serial` / `bail`**：前两者是异步场景的产物，宿主主线程是同步的；`bail`（返回首个非空结果）可由 Waterfall 表达，不值得多一个模式。

```cpp
// Emit
ctx.Emit(WorldLoadedEvent{ .World = worldId });

// Waterfall：每个 handler 决定是否继续（示意；语义已锁定，确切签名见 13.2）
float result = ctx.Waterfall<DamageQuery>(
    DamageQuery{ .Target = id, .Amount = base },
    [](DamageQuery& q, Next next) { q.Amount *= 0.5f; return next(); });
```

## 7. Effect 与作用域

### 7.1 Effect 是唯一的注册通道

**插件与 Vase 之间的一切交互，必须经过返回 `EffectHandle` 的注册入口。**

```cpp
EffectHandle ctx.Provide<T>(...)           // 注册服务
EffectHandle ctx.On<E>(handler)            // 订阅事件
```

注意**有两类东西不在这条通道上**：

- **进程级状态**——不走 Context，而是声明在插件的导出描述符里，随二进制加载而登记、随卸载而注销（原因见 9.1）。
- **面向宿主的注册**（界面面板、调试命令、快捷键……）——**Vase 核心不提供**。它们是宿主的概念，不是插件运行时的概念（见 0.1 的边界表）。宿主若需要，按同样的约定扩展自己的注册入口：**返回 `EffectHandle`、挂进当前插件的 `EffectScope`**。这样它们同样受「唯一通道」的保护，而 Vase 不必知道「面板」是什么。

**绕开这条通道的注册一律禁止**——例如插件自己把裸函数指针塞进某个全局表。

这条规则不是洁癖，是**卸载安全的前提**。插件代码可能以任何形式被 Vase 或其它插件持有；如果持有关系不在 EffectScope 的账上，卸载时就无法保证清零，而残留的调用就是崩溃。把所有注册收敛到一条通道，才能让「卸载安全」从祈祷变成**可证明**。

### 7.2 回收语义

| 性质 | 规则 |
|---|---|
| **归属** | 每个 Effect 归属创建它的插件的 EffectScope |
| **顺序** | 逆序回收（后注册先销毁） |
| **幂等** | `Dispose()` 可重复调用，第二次起无副作用 |
| **最终性** | 回收后不得再注册（Debug 下断言） |

逆序回收保证了「依赖先建立的后拆」；幂等保证了宿主反复 `DestroyPod()` 不会因为重入而出错——编辑器里 Play / Stop 会跑很多次，不幂等的销毁是 bug 温床。

### 7.3 提前释放

```cpp
EffectHandle h = ctx.On<DamageEvent>(...);
h.Release();          // 立刻执行回收动作，并从 Scope 的账上移除
```

**`Release()` 就是「立即回收」，不是一个更弱的操作。** 它执行该 Effect 的回收动作，**同时**把它从 Scope 的账上移除——这两件事是一个原子操作，不是两步。与随 Scope 一起 `Dispose` 相比，差别只有**时机**。

> 这两件事必须一起发生，缺一不可：只划账不执行动作，`Release()` 就成了「泄漏」的委婉说法；只执行动作不划账，Scope 销毁时会**二次回收**同一个 Effect。

提前释放之后，Scope 销毁时不会再碰它。

### 7.4 Effect 的存储形态

具体类型（`std::function<void()>` / 自定义的类型擦除句柄 / 模板化）见 13.1——纯性能问题，实现时测量决定。本文不指定它，但记下**唯一一条硬约束**：它必须能容纳插件 DLL 内的代码，因此**必须在 DLL 卸载前全部回收**——这正是 7.1 那条规则的直接推论。

### 7.5 子作用域：运行时的动态订阅

5.3 说了 Effect 的注册限制是**线程**而不是阶段。那么「进入某区域才订阅碰撞事件」这类运行时需求该怎么做？

```cpp
vase::EffectHandle scope = ctx.CreateScope();   // 它本身是父 Scope 的一个 Effect

scope.On<CollisionEvent>(&This::OnCollision, this);   // 挂到子作用域上
// ...
scope.Release();                                       // 用完手动回收
```

`ctx.CreateScope()` 返回一个**可手动 `Dispose` 的 `EffectScope`**，而它**本身注册为父 Scope 的一个 `Effect`**。于是：

- 用完 `Release` 掉，干净利落；
- **忘了 `Release` 也不会泄漏**——局结束时随父 Scope 一起回收，只是活得比预期久一点。

这条设计让纪律成立、出路也有了，**而且没有开出第二条注册通道**（7.1）：子作用域里的注册照样走同一个 `EffectHandle` 机制，照样在 Vase 的账上，照样参与 9.2 的计数。

> **唯一的限制**：`CreateScope` 只能在 Host 绑定的线程上调用（5.3）。这是它与「插件在自己线程里直接 `ctx.On`」的唯一区别——前者合法，后者违例。

### 7.6 Eject 时刻的回收（v3）

Eject 不引入新的回收机器——它只是让 7.1–7.5 那套机器在**局内**跑，而且是高频客户。三条由此显形的条款：

1. **拆除是局部的**：档 ① 保证被卸者无入边，`Eject(T)` 只碰 T 自己的 EffectScope。「跨实例的效果排序」问题在 Eject 路径上**结构性不存在**——那是级联重启才需要的机器（13.4 已否决）。
2. **出边在拆除期间有存活义务**：T 的 Effect 回收时可能合法地调用它依赖的 U 的服务（析构路径用依赖）。1.4 的串行保证 T 的 dispose 整体完成后才会有下一个生命周期动作——这是既有契约的推论，不是新机制。
3. **`Dispose()` 返回即永不重入**：线程 join、定时器 cancel、队列排空，**同步完成**。cordis 用 `inertia`（进行中的 Promise 锁）处理异步重入；Vase 借它的**问题**，不借它的机器——单线程串行 + 这条契约就是等价物。

第 3 条是 v3 新增的**承重条款**：v2 里异步残留有「进程快退了」兜底，v3 的 Eject 把兑现压力变成每一次热卸。违反它不会立刻炸——会在之后的某个时刻，以「回调踩进已解除映射的代码页」的形态现形，而那已经无法定位了。

## 8. 插件二进制与 ABI 约束

### 8.1 加载与卸载时机（v3）

| 事件 | 是否触碰二进制 |
|---|---|
| 枚举插件 / 求解依赖 / 校验 Preset | 否 |
| `CreatePod`（Catalog 已在扫描期解析过清单） | **进**（批装载） |
| `AdoptPlugin` | **确保驻留**（未驻留则单装；已驻留则复用镜像并做身份比对——5.6） |
| `DestroyPod` | **否**（二进制保留驻留——拆局不卸货，货留在架子上等下一局或等 Eject） |
| `EjectPlugin` | **出**（门槛：无实例存活 + 账上无反向边；证据见 8.2） |
| 宿主退出 | **出**（全部卸下，逐插件三档证据） |

**DLL 的进出由「需要重新编译 / 宿主增删插件」驱动，不再由局的生死驱动。** 但两条 v2 的安全前提原样继承，而它们正是 Eject 在 v3 仍然可证的理由：

- **一切生命周期动作串行于 Host 绑定线程**（1.4）。Eject 发生时没有任何 Vase 代码在别处跑，「此刻没有线程在该 DLL 的代码页里」由构造保证——三平台证据链（8.2）能立住，最重的一块地基就是这条。
- **换被依赖者的路仍然封死**（档 ①，13.4）。v2 用「等全局静默」换来的安全，v3 用「只放行叶节点」换取——两者拒的是同一类事故，只是静默的粒度不同。

**「一个库装一个插件」与「一个库装 N 个插件」对 Vase 完全等价。** 两者都导出同一个入口 `VasePlugin_GetPlugin(id)`——前者只认一个 Id（`VASE_PLUGIN` 宏生成，3.1），后者认 N 个（由 VasePack 生成，8.6）。所以 `PluginHost` 的加载路径**只有一条**：

```text
加载二进制 → VasePlugin_GetPlugin(id) → 描述符 → 用描述符里的工厂实例化
```

这条统一是有意的：它让开发期的「每插件一个 DLL」和发布期的「合并成一个库」在 Vase 侧**没有任何差别**，也让 8.6 的打包工具成为一个纯粹的构建期问题。

### 8.2 卸载验证：三档证据链（v3）

v2 的卸货发生在四下无人的静默期；v3 的 Eject 发生在**别的插件还在跑**的现场。证据从一条变三档，每档各自可证伪，由 `PluginHost` 在 Eject / Adopt 时主动执行并写进报告：

```text
档一 · 实例归零   三平台同：账本无反向边 + EffectScope 空 + 存活对象计数 0。
                 计数非零即拒卸——POCO 对此只留了一句源码注释警告调用方，
                 v3 把它升格为机制。
档二 · 映射解除   Windows：FreeLibrary 后文件可覆盖写——**辅助判据**：抓引用计数残留
                 这类真问题够快够准，但会被「改名替换」骗过（旧文件对象改名后其镜像
                 映射依然有效，同路径新文件完全可写），探针与重载之间还有 TOCTOU。
                 Linux：  dl_iterate_phdr 条目消失（v2 降为交叉验证的那条，升为主判之一）。
                 macOS：  _dyld_image_count / 路径枚举条目消失（同构做法）。
档三 · 新代码生效  三平台统一的原语：**内存镜像身份特征 ↔ 磁盘文件身份特征**比对。
                 Linux：.note.gnu.build-id（经 dl_iterate_phdr 的内存程序头表直读，
                 无须 /proc）；macOS：LC_UUID（_dyld_get_image_header 遍历；链接器
                 必写，macOS 26 起缺失即拒载；fat binary 取对应 slice）；
                 Windows：PE 调试目录的 CodeView RSDS GUID+Age（内存与磁盘同物可读，
                 纯自实现）。
                 Adopt 内部默认执行，**复用驻留镜像的分支同样比对**（5.6）；结果载入 AdoptReport。
```

**档三的成因要精确陈述（v3 评审后按查证修订，替代 v2 时期与 M1 文档 3.3(4) 的因果措辞）**：「重载拿到旧代码」的机制是 **dlopen 命中缓存镜像、根本不重读磁盘**（POSIX 明文：同路径命中 ⇒ 同一句柄，引用计数++）。真实触发条件是——引用计数未归零、被其他已加载对象 `DT_NEEDED`、`RTLD_NODELETE`、`STB_GNU_UNIQUE`。**「静态 TLS 超量」是另一类失败**（`dlopen` 当场报 "cannot allocate memory in static TLS block"），发生在进场侧，与「换不掉」无关，两件事不可混为一谈。禁互链（8.7）已封死 `DT_NEEDED` 这条；`STB_GNU_UNIQUE` 是 libstdc++ 的做派（libc++ 线可显式 `-fno-gnu-unique`，入 13.2）。其余成因的共同点是：**档一、二可以全绿，只有特征比对分得出新旧**。Windows 的定位随之调整：档二降辅助，档三（RSDS）升**主判**——v2 那句「唯一不可伪造」在此收回，改名替换就是它的反例。

**身份特征是插件的构建要求**（13.2 登记）：MSVC 线 `/DEBUG`（无它则 RSDS 缺席）、Linux 线 `-Wl,--build-id`；macOS 天然满足。**特征缺失 = Adopt 直接拒绝**，报告指路补链接标志——响亮的失败，不做「跳过验新」的静默降级（内存哈希兜底记在 13.1，暂不设计）。

**档三失败的政策**：Adopt 失败，X 留在局外，局内其余插件健康无恙；报告明文给出标准逃生门——**重建整局**。不自动重试（掩盖不确定性），不自动重建局（违背「失败显式报告」0.3-5）。

**macOS 有比 glibc 宽得多的 neverUnload 清单**（dyld4；v3 评审的新发现，M5 实测判定）：ObjC/Swift 元数据、**带析构函数的静态对象（static terminators）**、主程序静态依赖、`RTLD_NODELETE`——命中时 `dlclose` **返回 0 但镜像永在**。纯 C++/libc++ 栈里的主嫌疑是 terminators：一个普通的全局 C++ 对象就可能触发。不设「禁用静态析构」的契约（对正常 C++ 伤得太深），登记为风险、由 M5 用真实测量回答「macOS 上哪些插件可热卸」（12.3、13.1）。

装载失败的诊断借鉴 POCO 的思路（1.5 借用登记，已批准）：加载器报错时由自写的 PE / ELF / Mach-O 解析器补一句「缺哪个依赖」，而不是只回一个 `dlopen failed`。这个解析器与 8.7 的导入表执法、档三的特征读取共用同一条镜像解析路径。

### 8.3 跨 DLL 的 C++ 约束

主路径是**纯 C++ 接口**（非 C ABI）。前提是插件与宿主：

- 用**同一工具链**构建（同编译器、同版本）
- 用**同一 CRT 配置**（MSVC 下 `/MD`，共享 CRT，保证跨模块 `new` / `delete` 落到同一个堆）
- 包含**同一份 Vase 头文件**——**这一条由 `HeaderVersion` 在加载时强制检查（3.1），不是靠自觉**

> 前两条靠构建系统约束（同一个 CMake 工具链），第三条靠机制。**只写前提不写检查，前提就是一句祈使句**——用旧头文件编译的插件，vtables 布局、结构体大小、枚举值都可能不同，而 8.2 的「文件可替换」验证对此一无所知。

在此前提下，额外纪律：

| 规则 | 理由 |
|---|---|
| 边界上不传所有权 | 不传 `std::unique_ptr` 跨边界；或明确配对约定 |
| 异常不跨边界 | 插件入口内部捕获，转成 `Result`（Vase 自己的插件：**返回** `Result`，无异常可抛，见 0.3 原则 7；由外部工具链构建、开着异常的插件见 13.3） |
| 优先 `std::string_view` / `std::span` | 少一次分配，也少一个 ABI 面 |
| 不在边界上依赖 `type_index` 的运行时比较 | 见 6.1 |
| **禁跨 DSO 使用 `dynamic_cast` / `typeid`**（v3 明文化） | RTTI 跨模块比较不可靠（附录 B）；8.7 的 `RTLD_LOCAL` 策略更会让它**静默**失效 |

### 8.4 C ABI：预留的边界收缩方案

C ABI **不是当前必需品**，作为未来扩展保留。它在以下情况才需要启用：

- 插件需要由**不同编译器或不同 Vase 版本**构建
- Vase 需要作为二进制分发给第三方插件作者
- 插件需要跨语言（Unity C#、Python 等）

代价：只能传 C 类型（`uint32_t` / `float` / `const char*` / 不透明句柄 / 函数指针 / C 结构体），生命周期必须手工管理，`std::string` / `std::vector` / `std::function` / Vase 的 C++ 类一律不可暴露。

采用方式是**收缩边界**而非替换内核：在纯 C++ 接口之外增加一层 C 导出，Vase 内部不受影响。

### 8.5 目标平台与插件的两种形态

**编译器与 C++ 标准库：**

| 平台 | 编译器 | C++ 标准库 |
|---|---|---|
| Windows x64 | `cl.exe` **或** `clang-cl.exe` | MSVC STL |
| Linux x64 | `clang` | `libc++` |
| macOS arm64 | `clang` | `libc++` |
| Android arm64 | `clang` | `libc++` |
| iOS arm64 | `clang` | `libc++` |

**角色与插件形态：**

| 平台 | 角色 | 开发 | 发布 |
|---|---|---|---|
| Windows x64 | 开发 + 发布 | 每插件一个 `.dll` | 组合成一个 `.dll` |
| Linux x64 | 开发 + 发布 | 每插件一个 `.so` | 组合成一个 `.so` |
| macOS arm64 | 开发 + 发布 | 每插件一个 `.dylib` | 组合成一个 `.dylib` |
| Android arm64 | **仅发布** | — | 组合成一个 `.so` |
| iOS arm64 | **仅发布** | — | 组合成一个 `.a`（静态库） |

> **两点需要留意。** 其一，`libc++` 不是 Linux 发行版的默认标准库（默认是 libstdc++），所以每个平台的工具链文件都要**显式指定**，不能依赖编译器默认。其二，Windows 上两种编译器是**同一 ABI 的两个前端**——都目标 MSVC ABI、都用 MSVC STL，所以宿主与插件可以一个用一个；而 libc++ 与 MSVC STL 是两套 ABI，跨不过去。**8.3 的约束因此准确地说是「同平台 + 同 STL」，而不是「同编译器」。**

**Vase 本体两套都构建。** Windows 上 `clang-cl` 与 `cl.exe` 各有一套 preset，两者的产物互相兼容。要求本体两套都跑通，是为了让上面那句「宿主与插件可以一个用一个」不只是纸面约定，而是**被持续验证的事实**——插件作者用哪个，本体就得先证明那个能编。两处操作差异要记住：**`cl.exe` 需要 VS Developer 环境**（`clang-cl` 不需要，它能自行发现 MSVC 头/库）；**`clang-cl` 是主构建**，`cl.exe` 那条线强制不了裸 `throw`（0.3 原则 7 的落地细节见 M0/M1 设计文档第 9 节）。

**两档形态各有理由**：开发期每插件一个库，才能做到 11.2 的「只重编这一个插件」；发布期合并成一个库，减少文件数、缩短加载、允许链接期优化。**这条分档对 Vase 是不可见的**（见 8.1 的唯一加载路径），它完全体现在构建系统里。

CMake 侧由**平台工具链文件**承载上面两张表——每个平台一份，指定编译器、标准库、目标三元组。

### 8.6 组合库：VasePack 与符号保活

`Tools/VasePack` 是 CocoaPods 式的**构建期**工具：输入是散落的插件，输出是**一个组合库**——`VasePlugins.dll` / `libVasePlugins.so` / `libVasePlugins.dylib` / `libVasePlugins.a`（命名理由见 11.3）。**Vase 本体不参与、也不被它编译**——组合库里只有插件，一个 Vase 的符号都不包含（只引用、不包含）。

**它的核心产物是那个统一入口的分发表**：

```cpp
// VasePack 生成。路由到各插件的唯一命名描述符（3.1）。
extern "C" VASE_EXPORT const vase::PluginDescriptor*
VasePlugin_GetPlugin(const char* id)
{
    if (std::strcmp(id, "Vase.Combat") == 0) return VasePluginDesc_CombatPlugin();
    if (std::strcmp(id, "Vase.Ai")     == 0) return VasePluginDesc_AiPlugin();
    return nullptr;
}
```

**这张分发表顺带解决了静态链接的保活问题。** 静态库按需提取——链接器只拉进「被引用到」的目标文件。而插件之间**不互相引用**（它们只通过 Vase 的服务表交互），所以不加干预的话，所有插件都会被判定为「没人用」而丢掉。业界对这个问题有两套解法：

| 解法 | 代表 | 代价 |
|---|---|---|
| **链接器开关** | `--whole-archive`（GNU ld）、`-force_load` / `-all_load`（Apple ld） | 依赖**每个使用者的构建配置写对**。漏一个就是「插件全没了」，而报错信息指向的地方与插件代码毫无关系 |
| **硬引用** | CocoaPods 文档里的 `[MyClass class];` 那一招 | 需要在生成的代码里显式提及每个插件 |

**VasePack 走第二条**：那张分发表显式调用了每一个插件的描述符符号，于是保活是一条真实的引用链，而不是一个构建标志：

```text
宿主代码引用 VasePlugin_GetPlugin
   → 分发表引用 VasePluginDesc_CombatPlugin
      → 描述符里的工厂函数指针引用插件的实现
```

**好处有三**：跨平台一致（GNU 的 `--whole-archive`、Apple 的 `-force_load`、MSVC 的段收集各不相同，引用链不需要这些）；使用者不必配置任何东西；不会因为漏加一个标志而在某个平台上静默失效。

> **唯一仍需交代的例外**：iOS 的产物是静态库（`.a`），最终由**宿主**链进 App。宿主必须真的引用到包导出的符号（正常做法就是把入口交给 `PluginHost`，见 8.1），那条引用链才成立。**这一条要写进 VasePack 的产物说明**，否则又会被误当成「加个 `-force_load` 就好了」。

### 8.7 符号可见性与链接纪律（v3）

热插拔把「符号污染」从卫生问题升格为**安全问题**——插件会反复进出，任何一条隐式耦合都是日后 Eject 假成功的伏笔。三条纪律，全部可机器执法：

| 纪律 | 内容 | 执法点 |
|---|---|---|
| **`RTLD_LOCAL`** | Linux / macOS 的 dlopen 一律 LOCAL。**不学 POCO 的 `RTLD_GLOBAL` 默认**——多插件同名符号互相劫持是它报告里的原话，对一个插件随时进出的框架不可接受。Windows 无此开关，天然走 import library | `Loader` 层封装，不给宿主选项 |
| **禁二进制级互链** | 插件只准链 Vase 本体一个库；插件 A 的导入表不得引用插件 B 的文件名。破了这条，加载器会替 B→A 拉一条**账本看不见的边**，还把引用计数焊死（Eject 当场假成功） | **Adopt 时读 PE / ELF / Mach-O 导入表，命中兄弟插件即拒**；与 8.2 的 missing-deps 诊断共用一个解析器 |
| **跨插件只走服务边** | 插件间的一切调用经服务解析（6.2，账本可见），不走裸符号引用 | 上一条执法 + `RTLD_LOCAL` 使符号边根本不可表达 |

**`VaseHost` 的交付形态随之定死：Linux / macOS 上编为共享库。** `RTLD_LOCAL` 下插件对 Vase 符号的导入需要可见的导出表，而可执行文件不导出符号（除非 `-rdynamic`——那又回到全局污染）。Windows 侧无此议题。**这与 M0 现状的口径**：M0 骨架已是双 DLL（`VaseSession.dll` → 随更名改 `VasePod.dll`、`VaseHost.dll`），Linux 线在 M0 未构建过共享形式的 VaseHost——M1 落地时同步（10 节状态说明）。

## 9. 进程级状态与诊断

### 9.1 静态状态必须分层

插件里可以有跨 Pod 存活的静态状态。**它们不全是问题**——纹理缓存、类型注册表、反射信息跨局存活是对的，发行版里它们本来就是进程级。真正危险的是**实例状态逃逸到进程**：实体列表、系统注册、事件订阅跨局存活，意味着上一局没拆干净。

因此契约不是「禁止静态状态」，而是**静态状态必须显式分层并登记**。

登记的位置很关键：进程级状态**在插件的导出描述符里声明**，由 `PluginHost` 在加载二进制时登记、在卸载时注销。它**不经过 Pod**——否则「进程级容器持有实例级对象」就有了一个合法入口，1.2 节的铁律会被从后门绕过。

定义写在插件里，由 3.1 的 `VASE_PLUGIN` 块通过 `.ProcessState` 引用进描述符：

```cpp
// 进程级状态表。生命周期跟着二进制走，不跟着 Pod 走。
constexpr vase::ProcessStateDesc kProcessStates[] = {
    {
        .Name     = "Vase.Combat.TypeRegistry",
        .Reset    = &TypeRegistry::Clear,     // 可被强制重置
        .Describe = &TypeRegistry::Stats,     // 供诊断展示
    },
};
```

这两行 —— 定义在这里、引用在 `VASE_PLUGIN` 里 —— 就是「进程级状态的登记跟着二进制走」的全部机制。它不经过 Pod，所以 Pod 反复建销不会碰到它。**v3 改了一点：`.Reset` 在 `EjectPlugin` 时被自动调用，重置了什么写进 `EjectReport`**——Eject 若不归零进程级状态，8.2 档三「重载如同首次」当场失效。未被 Eject 的二进制，其 `.Reset` 仍是宿主手工调用（跨局语义原样）。

| 类别 | 处理 |
|---|---|
| 登记过的进程级状态 | 跨 Pod 存活；在宿主中可见；可强制重置；参与诊断；**被 Eject 时自动重置并报告**（v3） |
| 未登记的可变静态 | **视为违规**。Vase 无法在语言层面禁止，靠约定与评审 |
| 实例级状态 | 一律挂在 Plugin / Pod 上，随 EffectScope 回收 |

**契约**：进程级状态必须**幂等**——Pod 重建时重复初始化不能出错，也不能累积。

**v3 追加一条硬契约：跨插件共享的任何值必须走服务边（受账本保护），不得经由进程级状态中转。** 否则会出现图上看不见的「语义依赖」——U 没声明依赖 T，手里却攥着从 T 的缓存派生的裸值（纹理句柄之类）；Eject(T) 重置缓存后 U 拿着陈旧值继续跑，账本与导入表都看不见这条边。v2 靠「卸货必在四下无人时」天然免疫，v3 的免疫不再免费，只能靠这条契约 + `EjectReport` 的提示面兜底。

### 9.2 诊断基线

`DestroyPod` 时断言所有 Vase 可见的计数回到基线：

```text
Effect 数               → 0
服务注册数              → 0
事件订阅数              → 0
插件实例数              → 0
EffectScope 数          → 0
（可选）分配计数        → 基线
```

任何一项不为零 → 报告「上一局泄漏了 N 个 Effect，归属插件 `Vase.Combat`」。

**基线是「Pod 创建时」的快照，不是「进程启动时」的。** 理由：9.1 允许进程级状态跨 Pod 存活（纹理缓存、类型注册表），进程的内存占用本来就会单调增长；用进程启动值做基线会**永远报警**。只有以 Pod 创建时为基准做差分，才能只惩罚「本局漏掉的」——**那才是诊断想抓的东西**。v3 的 Adopt / Eject **不移动基线锚点**（仍是局的边界），但每一次进出都记进诊断事件流：局末差分若不为零，报告必须能回答「中途进出过谁」。

**计数始终维护，断言只在 Debug——这不是取舍，是分工。** 计数器的维护成本只是几个整数自增，永远开着；断言属于 Debug 的语义，Release 下把结果放进返回给宿主的 `PodReport`、不中断。**如果诊断基线只在 Debug 存在，它就只能服务开发期**——而玩家现场的泄漏报告恰恰是最需要它的地方。9.2 自称「核心卖点」，只在 Debug 卖是没有说服力的。

**计数不需要原子、也不需要锁。** 1.4 的单线程契约加上 5.3 的阶段划分，保证了写入不并发——这是那条契约除「可断言」之外的第二个回报。**反过来说：谁要是日后为了「支持多线程装配」拆掉 1.4，9.2 会跟着一起垮**，而这两处的关联不是从代码上看得出来的。

**这不是附属功能，是框架的核心卖点之一。** 没有它，「干净关停」只是一句无法兑现的口号；有了它，违规在发生的**那一局**就被抓住，而不是等到几十次 Play 之后以某个无从查起的崩溃呈现。

### 9.3 无法被自动化验证的承诺

诚实起见，以下承诺**只能靠约定与评审**，诊断只能发现症状而非阻止发生：

- 插件作者不会绕开 Effect 通道注册
- 插件作者不会把实例状态藏在未登记的静态变量里
- 插件作者不会在 Effect 外部持有服务的裸指针
- **宿主不会跨 Pod 边界持有服务指针**（1.3）。这条同样不在 `PluginHost` 追踪器的视野里：1.2 的追踪器只看得住 Vase 自己的容器，宿主自己的成员变量它一无所知。宿主侧只能靠纪律——**每次要用服务就从 `ctx.Get<T>()` 取，不要缓存**
- **（v3）插件不把跨插件共享的值经由进程级状态中转**（9.1 追加契约）。这条边的两端都没有账本记录，Eject 的判定看不见它
- **（v3）`Dispose()` 返回即永不重入**（7.6）。异步残留无法在框架侧穷举检测——join 没 join、cancel 没 cancel，只有插件作者知道

这些是**契约束**，不是机制保证。文档不把它们写成「Vase 保证」，只写成「插件作者必须遵守」。

## 11. 构建与工具链

> **状态（2026-09-15 更新）：构建系统已落地（M0）**——CMake 4.4 + vcpkg manifest 模式 + 六个 preset（`win-x64-{clang,msvc}-{debug,release}`、`linux-x64-clang-{debug,release}`），仓库里是 `CMakeLists.txt`、`CMakePresets.json`、`Cmake/Toolchains/`（三个工具链文件）、`Cmake/Triplets/x64-linux-libcxx.cmake`；双平台已跑通，与 13.2 的「已决定」一致。**真实可用的构建 / 测试 / 检查命令见 `CLAUDE.md`「构建与测试」**，本节不复述。
>
> 下面这一节剩下的内容（`VaseCli` 的子命令、重编译单个插件的流程、`VasePack` 的产物形态）**仍是提议**——M0 只落了构建地基，这些工具一个都还没实现。

### 11.1 `VaseCli`

```text
VaseCli scan     <插件目录>     加载每个 DLL、读出描述符、生成 .plugin.json

VaseCli validate <插件目录>     校验四项：
                                  · 清单与二进制是否一致、schemaVersion 是否兼容
                                  · 插件 Id 是否重复（3.4）
                                  · 依赖图、循环依赖、版本是否满足（6.3）
                                  · 服务/事件的命名前缀是否与插件 Id 自洽（6.1）

VaseCli plan     <preset>       输出加载计划：谁被加载、谁被【静态】跳过、为什么

VaseCli doctor                  环境诊断，检查四项：
                                  · 工具链一致性（编译器 / 版本 / CRT 配置）
                                  · HeaderVersion 与已构建的插件是否匹配
                                  · 插件目录的可写性（重编译要能替换文件）
                                  · 是否存在残留的文件锁（上一轮卸载没干净）
```

> **`validate` 与 `plan` 必须与运行时用同一套规则。** 它们和 `PluginHost`、`PluginCatalog::Solve` 共用实现（4.4）——工具说没问题、运行时拒绝，是这套流程最容易出的分歧，也是 3.4 整条链路建在「两边结论一致」上的原因。

`scan` 在构建后自动运行（CMake 后置步骤），保证清单与二进制同步。

### 11.2 宿主重编译单个插件的流程（v3：全程局不死）

这是 Vase 存在的主要用例。v2 的流程要先拆整局；v3 的叶插件重编译**只动目标插件，其余实例全程存活**：

```text
1. EjectPlugin(pod, X)          ← 账本执法（5.6）；档一、档二证据随 EjectReport 交付
2. 调用宿主的构建系统编译该插件   ← Vase 不负责这一步（用什么构建系统是宿主的自由）
3. VaseCli scan 重新生成清单     ← CMake 后置步骤自动跑（11.1），保证清单与二进制同步
4. AdoptPlugin(pod, X)          ← 清单↔描述符比对（3.4）+ 导入表执法（8.7）+ 档三身份特征验新
```

四步之外没有别的准备动作：**没有「先销毁局」**——X 无入边才走得进第 1 步，这正是 Eject 的执法内容；**没有手工验锁**——Windows 的文件锁检查是 Eject 档二的自动环节（v2 流程的第 3 步升格为机制）。

**被依赖的插件走不进第 1 步**——Eject 带着消费者名单直接拒绝，拒绝报告即答案（5.6 规则 ③）。

### 11.3 `VasePack`

发布期的组合工具（详见 8.6）。输入是散落的插件，输出是**一个库**——Vase 本体不参与、也不被它编译。

```text
VasePack pack <插件列表> --output VasePlugins
    · 把各插件编成静态库（或复用已有的目标文件）
    · 生成统一入口的分发表 —— 这一步同时就是「保活」所需的硬引用
    · 链接成一个库
```

产出按平台命名：

| 平台 | 产物 |
|---|---|
| Windows | `VasePlugins.dll` |
| Linux / Android | `libVasePlugins.so` |
| macOS | `libVasePlugins.dylib` |
| iOS | `libVasePlugins.a` |

> **命名刻意与框架本体区分。** 框架本体是 `Vase.dll` / `libVase.so`（10.2），组合库是 `VasePlugins.*`——**两者是不同的产物**：Vase 本体不参与打包（8.6），组合库里只有插件。叫成 `Vase` 会让人以为「这就是 Vase 库」，而它其实一个 Vase 的符号都不含（只引用、不包含）。

**它属于构建期，不属于运行时**：产出的就是一个普通的动态库（iOS 上是静态库），里面没有任何 Vase 专有的东西——除了那张分发表。

**它只依赖清单**（插件 Id、二进制名），所以与 `VaseCli` 共享 `PluginCatalog` 的清单解析。4.1 说 JSON 依赖落在 Catalog 层，这里又一次付了利息。

## 12. 验证策略

Vase 的核心承诺是**运行期性质**，而运行期性质只能由运行期证据证明。本节列出每条设计承诺对应的验证方式，并标出哪些是**承重的**（过不了说明框架不成立，而不是「有个 bug」）。

| # | 承诺 | 验证方式 | 承重 |
|---|---|---|---|
| **核心承诺** | | | |
| 1 | 反复 create / destroy Pod 无残留 | `Tests/Lifecycle`：建销 N 次后断言全部计数归零 | **是** |
| 2 | 卸载后二进制真的可释放 | `Tests/Abi`：卸载后以写方式打开文件 | **是** |
| 3 | 重载后拿到的是新代码而非缓存（8.2 档三） | `Tests/HotSwap`（见 12.1） | **是** |
| 3a | 局内 Eject / Adopt 不伤及相邻实例（v3 档 ①） | `Tests/HotSwap`：三插件局中对叶做 50 轮 Eject+Adopt，断言其余实例的计数与行为不变 | **是** |
| 3b | 账本执法：未声明解析被拒；声明未用仍拦 Eject；拒绝报告点名消费者（5.6） | `Tests/Integration` | **是** |
| 3c | Eject 后不再有回调命中已卸代码（7.6 永不重入） | `Tests/HotSwap`：带 10ms 定时器的插件被 Eject 后再跑 100 个 tick | 是 |
| 3d | Eject 自动重置登记的进程级状态并写入报告（9.1） | `Tests/HotSwap` | 是 |
| 3e | Adopt 拒绝导入表含兄弟插件的二进制（8.7） | `Tests/Abi`：伪造导入表的 fixture | 是 |
| 4 | 静态预测与运行时装配的分歧**只**出现在「运行时失败」时（4.4） | `Tests/Integration`：同一输入下 `VaseCli plan` 与实际装配逐项比对；再注入一个 `OnLoad` 必失败的插件，断言分歧**恰好只在那里** | **是** |
| **装配语义** | | | |
| 5 | `OnStart` 失败时下游被递归拆除，不留半活插件（5.2） | `Tests/Integration`：构造 `A→B→C`，令 B 的 `OnStart` **返回错误**（`OnStart` 返回 `Result<void>`，见 3.1；D17 之后「抛错」不再是可行做法——`try` / `throw` 在 Vase 的编译设置下基本是硬错误，只有 cl.exe 的裸 `throw` 是已知漏网，见根 `CMakeLists.txt`），断言 A、C 均回 `Skipped[运行时]` 且 `EffectScope` 已空 | **是** |

| 7 | 拓扑排序正确 | `Tests/Integration`：构造多级依赖图 | 否 |

| **生命周期与清理** | | | |
| 9 | 进程级状态跨 Pod 存活且幂等 | `Tests/Lifecycle`：登记状态，反复建销，断言行为一致 | 是 |
| 10 | 泄漏可被诊断定位到插件 | `Tests/Lifecycle/fixtures/LeakyPlugin` | 否 |
| 11 | 子作用域忘记 `Release` 不泄漏（7.5） | `Tests/Lifecycle`：创建子作用域、不释放、销毁 Pod，断言计数归零 | 否 |
| **边界与防护** | | | |

| **无法验证** | | | |

第 4 与第 5 条是这份表里最有价值的两条——它们是**唯一能证伪「砍掉 `epoch`」这个决定的测试**。如果第 5 条过不了（下游拆不干净），说明我们低估了装配期的复杂度，`epoch` 那套机制就得请回来。v3 加了对偶的一条：**3b 过不了（账本执法不住），要请回来的就是级联重启（档 ②）**——先让证据说话，再动架构。

### 12.1 `Tests/HotSwap` 是唯一能证伪核心承诺的测试（v3）

预先构建两个版本的 fixture 插件（A 与 A′）与一个无关邻居 B，A′ 中某个服务的返回值与 A 不同：

```text
构建 A、A′ 与 B
  → CreatePod{A, B}               ← B 与 A 无依赖关系，故 A 是叶
  → 断言行为 == A，且 B 的心跳 / 计数正常
  → EjectPlugin(A)                ← 三档证据：档一、档二在此结算
  → 用 A′ 覆盖 A 的文件           ← 这一步本身就是「锁真的解了」的断言
  → AdoptPlugin(A)                ← 档三：内存镜像身份特征必须 == A′ 磁盘特征
  → 断言行为 == A′（不是 A）
  → 断言 B 的实例从第一步起从未被碰过   ← v3 新增的最后一条：相邻性是承诺的一部分
```

它同时覆盖上表的第 1、2、3、3a、3c、3d 条，且**不可能被单元测试替代**——必须有真实的二进制、真实的卸载、真实的文件替换。

> 这个测试过不了，Vase 的核心承诺就不成立，其余一切都没有意义。

**两个版本怎么产出**：两个 CMake target（`VersionedA` / `VersionedAPrime`），源码只差一处（某个服务的返回值），编译到**不同目录但产物同名**；测试在运行时把 A′ 复制到 A 的位置覆盖。

**为什么不在测试里调编译器**：那会引入工具链依赖、几十秒延迟，以及「编译失败算谁的测试失败」这个无解问题。预构建把不确定性挡在测试之外。

> **这条我把握不算高。** 「DLL 同名、不同目录、运行时覆盖」在不同平台上的行为需要逐一验证（尤其是 macOS 的 bundle 结构）。它是目前唯一不依赖构建系统的方案——**实现时若发现某平台不可行，要回来改这一节**，而不是把测试降级成「两个不同名的 DLL」。

### 12.2 测试的层次

| 目录 | 证明什么 | 需要真实二进制 |
|---|---|---|
| `Tests/Unit/` | `ConfigBlob` 合并、`Error`、回收顺序、`Result` | 否 |
| `Tests/Integration/` | 求解、拓扑、跳过分类、清单校验、失败语义 | 部分 |
| `Tests/Lifecycle/` | 反复建销、计数归零、子作用域、诊断归属 | 是 |
| `Tests/HotSwap/` | Eject、替换、Adopt（三平台档二 / 档三） | **必须** |
| `Tests/Abi/` | 跨 DLL 解析、文件解锁、导入表执法 | **必须** |

**「需要真实二进制」这一列才是这张表的重点。** 前三类可以跑得快，后两类慢且平台相关——它们的**运行频率应该不同**。v3 的一处上调必须写明：v2 里 `Tests/Reload` 是「不必每次提交都跑」的尾部测试；**热插拔升为主干承诺后，`Tests/HotSwap` 自 M1 起按主干对待**——每次改动 Loader、账本、Eject 路径、描述符布局或 `HeaderVersion` 时必须跑，三平台各自留证据。

### 12.3 里程碑吸收（v3）

热插拔不进尾巴。各里程碑的增量（详细计划以 M0/M1 设计文档的后续修订为准）：

| 里程碑 | v3 增量 |
|---|---|
| M1 闭环 | + 单插件 Eject / Adopt 全循环，三档判据首次于 **Win / Linux** 跑通（macOS 的 neverUnload 风险面见 8.2，M5 判定）——**热插拔是骨架，不是尾巴** |
| M2 求解 | + 依赖账本执法与解析记录（3b） |
| M3 多插件 | + 叶判定的图反查与拒绝报告（3a） |

## 13. 未定、待实现、与明确不做

本节分三类。混在一起是上一版的毛病——「还没决定」和「决定不做」在读者眼里长得很像，但它们的含义完全相反。

### 13.1 尚未决定

- **`Effect` 的存储形态与分配成本**——纯性能问题。7.4 已记下约束（必须能容纳插件 DLL 内的代码、必须在卸载前全部回收），具体类型（`std::function` / 自研类型擦除 / 模板化）实现时测量决定。
- **平台差异的收口方式**——8.5 定了编译矩阵，但若干差异还没落到具体接口上：Unicode 路径、大小写敏感的文件系统、路径分隔符、动态库扩展名与加载 API 的差异。约定是「全部收在 `Loader` 层」，但那条约定本身还只是一句话。v3 给它加码了：`Loader` 现在还要承载三档证据（8.2）与导入表执法（8.7），这条收口约定的分量比 v2 重得多。
- **身份特征缺失时的内存哈希兜底（v3）**——特征已是构建要求（8.2、13.2），但「无特征的旧二进制」是永远被拒还是有哈希兜底，未决。暂不设计，出现真实需求再议。
- **macOS 热插拔能力上限（v3）**——dyld4 neverUnload 的条件清单远宽于 glibc（ObjC/Swift、static terminators、主程序静态依赖），且 `dlclose` 返回 0 不可信。「哪些插件在 macOS 上可热卸」由 M5 实测回答；机制与风险段见 8.2。

### 13.2 已决定，待实现

| 项 | 决定 |
|---|---|
| 构建系统 | CMake + vcpkg；编译矩阵由平台工具链文件承载（8.5） |
| 目标平台 | Win x64 / Linux x64 / macOS arm64（**开发 + 发布**）；Android arm64 / iOS arm64（**仅发布**）。工具链见 8.5 |
| 插件形态 | 开发期每插件一个动态库；发布期由 VasePack 组合成一个库（8.5 / 8.6） |

| 插件身份特征 | 构建要求：MSVC `/DEBUG`、Linux `-Wl,--build-id`（macOS 天然 LC_UUID）；缺失 = Adopt 拒绝；`-fno-gnu-unique` 一并入构建模板（8.2） |

### 13.3 已知的静默失败点（已接受）

**配置与进程级状态靠 `VASE_PLUGIN` 里的显式引用**（`.Config = vase::FieldsOf<T>`、`.ProcessState = kProcessStates`）。忘写不会编译报错、不会加载失败——插件照跑，**只表现为宿主界面上的配置面板凭空消失**，而现有的加载期比对拦不住（3.1 末）。

结构性修法是让配置宏直接绑定到插件类（`VASE_CONFIG(CombatPlugin, CombatConfig)`），于是**没有一行可遗漏的引用**；代价是 `VASE_CONFIG` 必须写在 `VASE_PLUGIN` 之前。

**当前选择接受这个风险**——因为后果在开发早期一撞就发现，而切换成本很低（下游读 `kFields`，与宏无关）。这是一条**有意的取舍，不是遗漏**。

**插件作者从插件里抛异常。** 宿主以关闭异常的方式编译（0.3 原则 7），而 8.5 明确允许插件由 `cl.exe` 或 `clang-cl` 构建——插件作者若用默认开启异常的编译器构建、并且真的 `throw`，异常会穿过**没有异常支持的栈帧**，是未定义行为，且宿主在加载期无法检测。这条属于 9.3 意义上的**契约束**：只能靠文档约束插件作者，不能靠机制拦截。

（与它相邻的另一条残余风险仍待实测：Linux 侧 libc++ 自身是**带异常**编译的，其内部的抛错路径若被触达，同样会穿过我们关闭异常的栈帧。正向路径已在 M0 实测正常，错误路径的行为留待 M1 实测——见 M0/M1 设计文档。）

### 13.4 明确不做

写下来是为了防止它们以「漏了」的形式回来：

- **C ABI**——预留的边界收缩方案（8.4），当前不启用
- **引擎适配**（UE5 / Unity / Godot）——它们**是宿主的示例**，不属于 Vase 本体
- **级联热替换与强制 Eject（档 ②）**——卸一个插件连带重启它的依赖方。v3 只放行叶节点（档 ①，5.6）；本条从 v2 的「热替换单个插件」改写而来，语义要读准：**叶热替换已是核心承诺，级联热替换仍然不做**
- **epoch / 稳态服务自动重载 / 依赖方原地重绑定（档 ③，全量 HMR）**——账本从源头拒绝制造上下线（5.6），对照见附录 A.2
- **Android / iOS 的任何热插拔**——档 ① 也不给移动端例外（12.3 M5；Apple 平台禁下载代码 dlopen）
- **Pod 嵌套**（2.3）
- **一个进程多个 `PluginHost`**（1.4）
- **一个服务标识多个实现**（2.3 第 4 条）
- **进程级状态在宿主侧的展示形态**——宿主界面怎么画，是宿主的事；9.1 只保证「可被登记、可重置、可描述」

## 附录 A：与 cordis 的对应与取舍

Vase 的设计借鉴了 cordis（一个 TypeScript 元框架）的若干思路。本附录给熟悉 cordis 的读者一张地图，同时记录取舍的**理由**——避免读者把「有意不做」误认为「漏了」。

### A.1 借鉴了什么

| cordis 的思想 | Vase 的对应 | 说明 |
|---|---|---|
| 一切副作用统一为可回收对象 | `Effect` + `EffectScope` | 全库通用语。`ctx.on` / `ctx.provide` / `ctx.timeout` 都返回 disposer |
| 副作用树与生命周期树同构 | EffectScope 随插件销毁 | 不需要手工维护资源清单 |
| 逆序回收 | 同 | 「后注册先销毁」是关停顺序正确性的来源 |
| 服务即能力单元，经 Context 解析 | 同 | 插件不直接互相引用 |
| 声明式依赖 + 拓扑加载 | 同 | `requires` → `LoadPlan` |
| 插件是纯粹的声明 | 同（`.plugin.json`） | 元数据与代码分离 |

### A.2 明确不做的

| cordis 机制 | 为什么 Vase 不做 |
|---|---|
| **Fiber / epoch 指纹** | epoch 解决「服务上下线时依赖方自动跟随重载」。Vase 的服务**只在装配期**（`Load` + `Start`）可能消失，那一段用 5.2 的一次性递归拆除就够了——**装配期的消失是可枚举的、发生一次**，而 epoch 要解决的是**稳态运行期**的反复上下线。v3 引入叶热插拔后这条论证反而更干净：**账本在进出那一刻就拒绝制造上下线**（有依赖即拒卸，5.6），上下线仍只发生在装配期——epoch 依旧没有触发场景 |
| **`isolate`（同名服务多实例）** | 为「单进程多租户」设计。Vase 的宿主一进程一 Pod，多实例场景用「显式 Realm 对象」即可覆盖，不值得抬成主线 |
| **`intercept`（配置沿作用域覆盖）** | 同上，且 Vase 的配置在 Pod 创建时冻结 |
| **原型链作用域 + `Proxy` 惰性解析** | C++ 没有原型链与 `Proxy`。Vase 用显式 `Get<T>()` 替代，代价是失去「读未定义属性即解析」的语法糖，收益是没有隐藏的运行时魔法 |
| **配置树 / Entry / EntryTree / 文件双向同步** | 这套机制（journal、drain 循环、原子写、冲突对账）是为「配置文件既是用户编辑器又是运行时程序」设计的。Vase 的 Preset 是纯内存读取，不需要写回 |
| **HMR 三级重载** | 全量对齐不做：它依赖 Node 的模块缓存失效，且要求依赖方**原地重绑定**（档 ②/③ 的地盘，13.4 已否决）。v3 的叶 Eject / Adopt 是它的**受限子集**：只换无人依赖者、状态不迁移、级联不存在（5.6）。cordis 三级里被 v3 吸收的是**协议形状**而非运行时——「先全量校验再进场；进场失败不回滚、干净退出」（对应其 partialReload 阶段 1-3 的骨架） |
| **「插件即值」的插件形态** | cordis 的插件是一个运行时**值**（函数／类／对象），`inject` / `Config` 作为属性挂在它身上直接读。**这一条不是「不做」，是 C++ 做不到**——DLL 导出是符号级的，导出的是函数地址，不是「一个可以直接调用的东西」，也没法把属性挂在函数上。所以 Vase 改为「类 + `VASE_PLUGIN` 宏 + 生成的清单」，见 3.1 |

### A.3 术语对照

**Vase 的术语不与 cordis 同步**，因为同名词不同义比不同名更危险——熟悉 cordis 的读者会自信地按旧语义理解，然后在前三节就走错。术语处理分四类：

| 类别 | 处理 | 例子 |
|---|---|---|
| 语义一致 | 沿用 | `Plugin`、`Service`、`Event`、`Effect` |
| 同名不同义 | 沿用名字，但**在首次出现处就地划界** | `Context`（见 2.3） |
| cordis 有、Vase 没有 | 正文不出现，仅本附录说明 | `Fiber`、`epoch`、`isolate`、`intercept`、`Realm`、`Entry`、`EntryTree` |
| Vase 有、cordis 没有 | 直接造词 | `PluginCatalog`、`PluginHost`、`Pod`、`EffectScope`、`Preset`、`LoadPlan` |

### A.4 定位差异

cordis 是**元框架**：它提供组装应用的运行时，上层框架在其上定义服务与插件，宿主长期存活、配置驱动、运行期可任意装配。

Vase 是**能力库**：它被宿主嵌入，宿主决定何时装配、何时拆解，v3 起还包括**局内的受控进出**。Vase 不假设宿主的形态；但它现在假设插件集合会在局内变化（档 ①），并为这个假设配了账本与证据链。

两者的形态差异（动态语言 vs 静态语言、有 GC vs 无 GC、长期驻留进程 vs 反复建销实例）使得**机制可以借鉴、结构不能照搬**。Vase 保留的是「副作用统一管理、依赖声明式解析、生命周期完全拥有」这三条思路，其余按 C++ 的现实重新设计。

## 附录 B：C++20 落地备忘

实现时需要正面处理的 C++ 特有问题，逐条记录，避免重复踩坑。

| 问题 | 说明与对策 |
|---|---|
| **`type_info` 跨 DLL** | `std::type_index` 的跨模块比较依赖编译器实现。Vase 的服务标识与**事件标识**都改用字符串常量 + 整数版本（6.1 / 2.4），不依赖它 |
| **旧头文件编译的插件** | vtables 布局、结构体大小、枚举值都可能与当前头文件不同，而 8.2 的文件锁验证对此一无所知。由描述符里的 `HeaderVersion` 在加载时拦截（3.1 / 8.3）——**这是「同一份头文件」这条前提唯一的执行点** |
| **CRT 与堆** | 跨模块 `new` / `delete` 只有在共享 CRT（MSVC `/MD`）下才落到同一个堆。8.3 把它列为约束。**注意约束的准确范围是「同平台 + 同 STL」，不是「同编译器」**——Windows 上 `cl` 与 `clang-cl` 目标同一 ABI，可混；libc++ 与 MSVC STL 跨不过去（8.5） |
| **静态库的「按需提取」** | 链接器只拉进**被引用到**的目标文件。插件之间不互相引用（只通过 Vase 的服务表交互），所以不加干预会被全部丢掉。VasePack 用生成的**分发表**制造硬引用（8.6），而不是靠 `--whole-archive` / `-force_load`——后者依赖**每个使用者的构建配置**写对，漏一个就是「插件全没了」，且报错指向的地方与插件代码毫无关系 |
| **`FreeLibrary` 的不可验证性** | 返回值不保证卸载干净。可信的是 8.2 的三档——而 Windows 的档二（「文件可替换」）也只是**辅助**信号（改名替换可骗过它，v3 修订），主判是档三特征比对 |
| **glibc 缓存镜像复用（v3 归因修订）** | 真实成因：引用计数未归零、被其他对象 `DT_NEEDED`、`RTLD_NODELETE`、`STB_GNU_UNIQUE`——`dlopen` 同路径直接返回同一 link_map、不重读磁盘。「静态 TLS 超量」是 **dlopen 侧的分配失败**，不是驻留成因（M0/M1 设计文档 3.3(4) 的措辞已列入勘误）。对策：8.2 档三特征比对；禁互链已封 `DT_NEEDED` 路径 |
| **macOS dyld4 neverUnload（v3 新增行）** | ObjC/Swift 元数据、带析构的静态对象（terminators）、主程序静态依赖、`RTLD_NODELETE` → `dlclose` 返回 0 但镜像永在。纯 C++ 线的主嫌疑是 terminators；不设禁用契约，M5 实测判定（8.2、12.3） |
| **`RTLD_GLOBAL` 符号劫持（v3 新增行）** | POCO 的默认策略在多插件反复进出的框架下不可接受。对策：8.7 定为 LOCAL，跨插件交互只剩服务边 |
| **静态初始化顺序** | 插件 DLL 里的静态对象在 `LoadLibrary` 时构造。如果它们依赖 Vase 的全局状态，顺序不可控。约定：插件静态对象不得依赖 Vase 的状态 |
| **静态析构与卸载** | DLL 卸载时静态对象析构，若析构函数引用了已被卸载的其它模块的代码，会崩溃。约定：静态对象间不得跨模块互相引用 |
| **异常跨边界** | Vase 自己的插件入口**返回** `Result`——D17 关闭异常之后没有异常可抛，「捕获并转换」是 13.3 里那类外部工具链插件的处置（契约束，机制拦不住） |
| **`std::function` 的分配** | Effect 若用 `std::function<void()>` 承载，每次注册有一次分配。是否值得优化取决于诊断数据，先测量再决定 |
| **线程** | 一切 Vase API 只在 `PluginHost` 绑定的那个线程上合法（1.4）。若插件在 `OnStart` 起线程，必须在同一插件内用 Effect 保证线程先于服务注销而停止（5.4），且该线程**不得回调 Vase**——要回调就先把工作投递回绑定线程。这条契约不是建议：9.2 的计数器不做原子，靠的正是它 |
| **`std::string_view` 的生命期** | 边界上优先 `string_view`，但插件不得返回指向自己内部缓冲区的 `string_view` 给宿主长期持有 |

### B.1 命名与引擎术语的冲突备忘

接入游戏引擎时，Vase 的层名会与引擎的既有术语共存。命名前应先对照引擎的层名，避免「同一个词落在不同的轴上」——这类冲突不会让代码出错，但会让读者自信地理解错。

| 名字 | 判定 | 说明 |
|---|---|---|
| ~~`Runtime`~~ → **`Session`**（v2 时期） | **已改名（历史，已被下一行取代）** | 三大引擎都拿「Editor vs Runtime」当基础分层：UE 的 `.uplugin` 里 `Modules[].Type` 的取值就包含 `Runtime` / `Editor` / `Developer` / `Program`（那里 `Runtime` 说的是**打包分类**，即「这个模块打进发行版」），Unity 有 Runtime / Editor assemblies，Godot 有 `@tool`。Vase 的 `Runtime` 说的是**执行实例**——同一个词，两个轴。此外「Vase runtime」作为整体产品的俗称会与内部分层名打架。改为 `Session` 后，「Host 创建 Session、销毁 Session」既自然又暗示有界生命周期 |
| ~~`Session`~~ → **`Pod`** | **v3 改名（需求方拍板）** | 双动因：其一，「Session」在游戏 / 网络语境里先被读成对局会话、网络会话——Vase 明文不提供业务语义（0.1），名字不该邀请错误联想；其二，v3 的热插拔让这层的语义从「整体生死」变为「批量主干 + 叶进出」，需要一个不预设「同生共死」的名字。选词判据沿用 `Runtime` 那次：不撞引擎分层词、不与产品俗称打架、「Host 创建 / 销毁 X」读得顺、暗示有界生命周期。**中文量词不变，仍为「局」**。**k8s 先例（被组装的临时单位、只建与毁）是加分项，但有三处不守，词表必须辟谣**：① 无滚动替换——换被依赖者直接拒（档 ①）；② 无副本并存——同名服务一局一实现（2.3 第 4 条）；③ **有局内部分增减**——Adopt / Eject 恰是 k8s Pod 没有的超集能力，防的是反向脑补（「Pod 都是静态的」）。派生名全集见 1.5 第 1 条 |
| **`Effect`** | **保留**（已知冲突） | 与 UE 的 `UGameplayEffect`（GAS 核心类）同词。保留的理由：`Effect` 在本文中出现频率极高，改名波及整篇；GAS 只在部分 UE 项目中使用。**若将来确定要接 UE 且会用 GAS，重新评估这条**——`Disposable` 是 C++/.NET/Rx 圈的标准备选 |
| `Plugin` / `Service` / `Event` | 安全 | 通用编程词汇，引擎侧无冲突语义 |
| `Context` | 安全 | 引擎无同名核心概念（Unity 的 `SynchronizationContext` 属 .NET，不冲突） |
| `Catalog` / `Host` / `Preset` | 安全 | 引擎无同名层名。UE 的「network host」是子系统概念，不构成层名冲突 |
| 已避开的坑 | — | `Instance`（UE 有 `UGameInstance`）、`World`（`UWorld`、Godot 的 `World2D/3D`）、`Environment`（游戏语境里即游戏世界）、`Scene`（Unity/Godot 场景）、`Module`（UE 模块） |

### B.2 配置宏反射的逃生口

3.2 选了内联元组的宏反射。它的主要代价是 **IDE 对宏展开成员的补全与跳转可能失效**。如果实际使用中这一点不可忍受，有一条现成的替代路径：**用配置 DSL 文件生成结构体与元信息**。

```jsonc
// config/CombatConfig.vasecfg.json
{ "fields": [
    { "name": "CriticalMultiplier", "type": "float", "default": 2.0, "min": 1.0, "max": 10.0, "label": "暴击倍率" },
    { "name": "FriendlyFire", "type": "bool", "default": false, "label": "友军伤害" }
]}
```

构建时生成 `CombatConfig.h`。作者仍然只写一处（没有违反「同一事实不写两遍」），而插件代码读到的是**真正的 C++ 声明**，IDE 完全正常。

| | 内联元组（当前选择） | 配置 DSL + 生成 |
|---|---|---|
| 作者手写 | C++ | JSON |
| IDE | 打折 | 完全正常 |
| 配置类型范围 | C++ 能表达的都行 | 受限于生成器支持的标量集合 |
| 基础设施 | 库内部的宏机制 | 一个代码生成器 + 构建步骤 |
| 新增格式 | 无 | `.vasecfg.json`，需版本化 |

**切换成本低**：下游读的是 `kFields`，与生产者无关。所以这条不必现在做，记在这里备用即可。

另有一条更重的路——**解析 C++ 头文件生成反射代码**（UE 的 UnrealHeaderTool 路线）。源码完全干净、IDE 完全友好，但需要写一个 C++ 头文件解析器，工程量以「周」计。UE 养得起它是因为除反射外还要生成 GC 集成、序列化与蓝图绑定；Vase 没有那么多要生成的，不值得。

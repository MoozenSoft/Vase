# 性能：口径、成本承诺、以及怎么测

**这份文件不是"零开销条约"。** 目标不是"所有代码零运行时开销"，而是：

> **Vase 对运行时成本有明确、可解释、可验证的工程约束。任何抽象都必须能说出自己的成本。**

禁止抽象（"不许用虚函数"、"不许用 std::function"）在这个项目里是错的——插件框架的存在本身就需要间接层。**要禁止的是"说不清成本的抽象"。**

---

## 1. 已经落在代码里的成本承诺

这些不是口号，是能从头文件读出来的具体约束。**改动它们 = 改设计，先问需求方。**

| 承诺 | 实现 | 出处 |
|---|---|---|
| **反复 play / stop 稳态零分配** | `ScopePool`：size-class 空闲链表，chunk 64 KiB，块对齐写死 16 | `Detail/ScopePool.h`（D8/D10） |
| **计数的维护不随构建模式分叉** | `DiagnosticCounters` **始终维护（Release 也写进 `PodReport`）**，断言只在 Debug | `Detail/Counters.h` |
| **服务与事件标识不碰 RTTI** | `kName`（编译期常量字符串）+ `kVersion`（`uint32`） | `Service/Service.h`、`Event/Event.h` |
| **描述符零堆、零副作用** | `MetaArray<T, N>`：自持 `std::array` 存储 + 长度，`constexpr` 可构造、可平凡拷贝 | `Detail/MetaArray.h` |
| **服务查找是一张扁平面** | 不沿 Context 上溯；一个标识一个实现 | `Pod/Context.h`（§2.3） |
| **事件派发同步、无队列、无分配** | `EventBus::Emit` 直接走订阅表 | `Detail/RegistryBus.h` |
| **虚分派面窄** | `Plugin` 只有 `OnLoad` / `OnStart` + 虚析构；`IEffect` 只有 `Recycle()` | `PluginDescriptor.h`、`Effect/IEffect.h` |
| **句柄可平凡拷贝** | `EffectHandle` / `PodHandle` 都是几个整数的聚合 | `Effect/EffectHandle.h`、`Pod/Pod.h` |

**账本与查找的线性扫是刻意的**：`DependencyLedger` 的注释写着"单线程契约下 `vector` 线性扫就是正确复杂度（M1 的边数以十计；**别预防性建索引**）"。服务表同理。

## 2. 代价是明写出来的，不是藏起来的

几条已知并接受的代价——**知道它们存在，比假装没有重要**：

| 代价 | 为什么接受 |
|---|---|
| 服务解析是**字符串比较**（`type_index` 不能用） | 跨 DLL 的类型标识不可靠。这是正确性换性能，不是懒 |
| 账本**粗粒度**：一次瞬态解析留下的边也拦 Eject | 细化（瞬态解析自动过期）是复杂度的黑洞，档 ① 不需要 |
| `/wd4251` 整 TU 免检 | 见 `abi-boundary.md` 第 6 节——是债，有还债条件 |
| `require` 形的服务解析失败即 `ProgrammerError` | 无异常编译下没有可恢复路径 |
| `MetaArray` 是**定容**的（各 16 条） | 溢出是编译错误。定容换来 POD 与零堆 |
| `PodReport::Clean()` 等少数成员函数定义在 `VasePod` 里 | 跨 DLL 调用一次，不是热路径 |

**判断标准**：新增的每一个"为了省事"的间接层，都要能说出它在**哪条热路径上、贵多少**。说不出来就不该加。

## 3. 什么时候该测

**Per.1 / Per.6：没有测量就不要声称性能，也不要为没有测量的性能做优化。**

具体到这个仓库：

- **仓库当前没有基准设施**（没有 benchmark target、没有基线数据）。所以"这样更快"在本仓库里**默认没有证据**，说的时候要标明是推理。
- 改到这些地方时才值得建基准或至少量一次：`ScopePool` 的块分配路径、`ServiceRegistry::Find` / `EventBus::Emit`、`DependencyLedger` 的扫、`Loader` 的镜像解析、Pod 的建 / 销循环。
- **"反复播放 / 停止"的稳态分配次数**是最有价值的那条指标——它是 D10 这条明写承诺的直接验证，且 `ScopePool` 的实现让它可以被计出来。
- 量的对象是**端到端的 play/stop 循环**，不是微基准里的单个函数。缓存效应与分配器行为在小基准里全被抹掉了。

**写进汇报时的措辞**：有测量就说"测得 X"并给出方法与数字；没测量就说"这是推理，未测"。**在性能上把推理说成事实，是这份 skill 最想拦住的一类报告失真。**

## 4. 结构性开销：优先看设计，不看微优化

比 §1 里那些细节更值钱的是这四条：

- **数据布局**：连续优于指针追逐。`std::vector<T>` 优于 `std::vector<std::unique_ptr<T>>`——除非多态或稳定性是刚需（`PluginHost::Slots` 用 `vector<unique_ptr<PodSlot>>` 正是为了**槽位地址稳定**，那是必要的，不是随意的）。
- **间接层数**：一次服务解析 = 字符串比较 + 线性扫 + 解引用。不要再叠代理层——`Context` 明确"无 Proxy"就是这条。
- **编译期能做的移到编译期**：`kName` / `kVersion`、`static_assert` 的形状校验、描述符的 `constexpr` 构造。
- **启动 / 关停的成本对称性**：Vase 的关停是逆序 `EffectScope` 回收，成本应当与注册数同阶。若某次关停出现"注册了 10 个、拆了 1000 次操作"，那是设计问题不是常数问题。

## 5. 反模式

- 用 `std::function` 承载**每一帧都会调用**的回调（`Context::On` 的 handler 是一次注册、多次派发，可接受；每帧新建 `std::function` 不可接受）。
- 在热路径上 `std::string` 拼接 / `std::map<std::string, ...>` 查找。
- 为"以后可能要"预先建索引、预先做对象池、预先加缓存层。**这个仓库的注释反复写着"别预防性……"。**
- 用 `std::endl`（强制 flush）。用 `'\n'`。
- 拿 `-O2` 当性能证明。构建模式不改变算法的复杂度。

## 6. 代码体积与二进制大小

热插拔对体积有额外的敏感度：**每个插件都是一个独立镜像**。

- 插件 target 只链 `VasePod`（D11）——这条同时是链接纪律与体积纪律：插件不该把 `VaseHost`（含 Loader、PE/ELF 解析器）拖进来。
- 模板实例化点要想着落在哪：`Context::Provide` / `On` 都是模板，实例化在**调用方 TU**；被它们取用的 `DestroyShell<Cell>` 同样是头里的成员模板，**一并落在插件 TU**，不会集中到 `VasePod` 里（见 `ownership-lifetime.md` 第 5 节）。这意味着每个用 `Provide` 的插件都带一份自己的实例化。
- 头文件里的大块模板实现会被每个包含它的插件复制一份。往 `Include/Vase/` 的公开头里加东西时，想一下它会被复制多少份。

# 插件生命周期与热插拔

这份是 Vase 独有价值最大的一块，也是**改动代价最高的一块**：`Loader`、依赖账本、`Eject` / `Adopt` 路径、描述符布局、`HeaderVersion` 这几类的改动，验证要求是 `Tests/HotSwap/` **全部**用例 + 双平台各自留证据（见 `verification.md`）。

## 1. 状态机（§5.2）

```text
Discovered   清单已知，尚未参与
     │
     │  ① 求解（纯数据，不执行任何代码）［M2 的 Catalog；M1 由手写 LoadPlan 代替］
     ├──► Skipped[静态] ──── 被 Preset 禁用 / 依赖不满足［M2 提案，M1 无此态］
     ▼
  Loading    加载二进制、执行 OnLoad
     │
     ├──► Failed ──┬── 立即回收本插件的 EffectScope            ← M1 只做到这一步
     │             └── 下游级联为 Skipped[运行时]［M2 提案：M1 不动下游］
     ▼
  Loaded     服务已注册
     │
     │  ② 全部进入 Loaded 后统一启动
     ▼
  Started    运行中
     │
     ├──► Failed ──┬── 立即回收本插件的 EffectScope
     │             └── 下游递归拆除［M2 提案：M1 两阶段处置完全相同］
     │
     │  ③ 关停：逆拓扑序回收 EffectScope
     ▼
 Stopping ──▶ Unloaded
```

**标了［M2 提案］的三行，磁盘上没有对应代码**：`Pod.h` 的 `LiveInstance::InstanceState` 只有 `kLoading / kLoaded / kStarted / kFailed`，全仓 `Skipped` 零命中，也没有任何拆下游的路径。M1 的真实失败处置见第 4 节——**照这张图写代码，会写出一个不存在的状态机。**

**`Failed` 不是真正的终态——它保留的是记录，不是实例。** 详见 `ownership-lifetime.md` 第 7 节。

## 2. 两阶段加载（§5.3）

```text
阶段 0            宿主注册回调（可选，CreatePod 传入 PodOptions::Stage0）
                    · 宿主的服务在这里注册，挂 Pod 根 EffectScope
                    · 此时还没有任何插件 Load —— 宿主服务天然先于插件可见
                       ↓
阶段 1（拓扑序）   OnLoad(Context&)
                    · 注册服务、订阅事件
                    · 可以安全使用「自己声明的依赖」所提供的服务（拓扑序保证它们已 Load）
                    · 但不得假设「非依赖」插件已就绪，也不得开始活动
                       ↓
阶段 2（拓扑序）   OnStart(Context&)
                    · 所有插件的 OnLoad 全部完成后统一开始
                    · 此时全部服务就绪，可以安全地使用任意服务
```

**阶段 1 的意义：把"服务注册"与"开始活动"解耦。** 只有一个阶段的话，插件 A 启动时发出的事件可能早于插件 B 完成订阅——而 B 在拓扑序上排在 A 之后完全合法。两阶段消除了这类时序竞态。

**阶段 0 的意义：宿主服务不需要伪装成插件服务。** 没有这个钩子，宿主只能让某个插件替它注册自己的服务——那会让"谁提供的"这个本该清晰的属性变得含糊，也会让宿主服务的回收归属无处安放。

**三个阶段都必须在 `PluginHost` 绑定的那个线程上执行。**

> **注册 Effect 的准确表述是"只允许发生在 Host 绑定的线程上"，不是"只允许在 `OnLoad` / `OnStart` 里"。**
>
> 装配期（阶段 0–2）自动满足这条；**运行期**通过 `ctx.GetScope()` 在同一线程上 `ctx.Provide` / `ctx.On` / `ctx.GetScope().Create<T>()` 同样合法。**限制的是线程，不是阶段**——写成"阶段"会把一条本来可用的能力误伤掉。

> ［提案，M1 未落地］§7.5 的 `ctx.CreateScope()`（返回可手动 `Dispose` 的子作用域，且它本身是父 Scope 的一个 Effect）**在代码里不存在**——M1 的 `Context` 只暴露 `GetScope()`，返回 Pod 已经建好的那个 `EffectScope`。

**实现细节别踩**：`CreatePod` 与 `Adopt` 共用装配件，但**回调必须留在调用方**——`CreatePod` 要求"先全 `OnLoad` 再全 `OnStart`"，把回调合并进 helper 会把那个序压掉。

## 3. 关停：不需要 `OnStop` 钩子（§5.4）

关停时**逆拓扑序**回收各插件的 `EffectScope`；回收顺序 = 注册顺序的逆序。

```text
OnLoad 里注册的 Effect     ──┐
OnStart 里注册的 Effect    ──┤ 注册更晚
                            ▼ 回收更早
```

一个在 `OnStart` 里启动线程的插件，只需把"停止线程"也注册为 Effect。它注册得比服务注册更晚，于是回收得更早——**线程先停，服务后注销，正好是正确的顺序**。

**这个顺序保证是"一切皆 Effect"换来的。手写 `OnStop` 反而给了写错的余地。**

**前提：构造函数不是注册副作用的合法位置。** 上面论证依赖"`OnStart` 里注册的 Effect 比 `OnLoad` 里的晚"。若插件在**构造函数**里起线程并注册了对应的停止 Effect，那个 Effect 会比 `OnLoad` 里的服务注册更早——回收更晚，线程就会在服务已注销之后继续跑。

## 4. 部分失败：M1 只有「无级联」，级联拆除是 §5.5 提案

**先把现状和提案分开。** 混淆这两件事正是本 skill 第一条纪律点名的失败形态，而这一节是它最容易发生的地方——因为提案的设计理由写得很顺，读起来就像在描述现状。

现状的执法点：`Source/Host/PluginHost.cpp` 装配段的 `recordFailure` + `continue`（`OnLoad` 失败与 `OnStart` 失败两处）、同文件 ⑥ 段的 `options.Strict` 分支、`Include/Vase/Host/LoadPlan.h` 里 `PodOptions::Strict` 的注释。

| 失败发生在 | M1 的处置 |
|---|---|
| `Loading`（`OnLoad` 里） | `DiscardInstance`（§5.2：Scope 先撤、实例后销毁、账本先摘）→ 落 `FailureRecords` → **`continue`** |
| `Started`（`OnStart` 里） | **一模一样**——同一套 `DiscardInstance` + 记录 + `continue` |

三件必须说清的「没有」：

- **没有 `Skipped` 这个态。** `Pod.h` 的 `LiveInstance::InstanceState` 只有 `kLoading / kLoaded / kStarted / kFailed`，全仓 `Skipped` 零命中。下游不会因为谁失败而变状态。
- **下游不被拆除。** `OnStart` 阶段失败时，下游早已注册了服务、订阅了事件——M1 **不动它们**，它们继续跑，Pod 照常交付（宽容是默认）。
- **失败实例留空壳条目**（`Instance` 已置空、条目仍在 `pod.Instances`）。那是 §5.2「保留记录」在装配点上的形态，也是 Eject 第 ②' 步要摘的那条——不是泄漏，但别当它不存在。

`Strict = true` 改变的是**整局命运，不是级联**：任一 `Failed` → 半成品整体拆除 → `CreatePod` 返回 `Err`。磁盘注释的原话就是「M1 是『无级联』的基本形（级联拆除等 M2 依赖图）」。

### 提案那一半（§5.5，未落地，别按它写代码）

wiki 设想的是两个阶段**处置不同**：`Loading` 失败 → 下游直接变 `Skipped[运行时]`（拓扑序保证它们还没开始）；`Started` 失败 → **递归拆除**，逆拓扑序回收下游的 `EffectScope`，可能连锁。理由本身站得住、M2 兑现时应当读它：**已经在跑的东西没有"变为 `Skipped`"这个选项，只能被拆掉**；那也是全设计里服务唯一会消失的时刻，`Context` 四条边界里「不做稳态运行期的服务自动重载」的限定词正为此而加——装配期内部服务仍可能消失。同理，失败清单要区分静态跳过与运行时跳过。

判断标准很短：**这一条在磁盘上有对应的状态或代码路径吗？** 级联、`Skipped[运行时]`、静态/运行时跳过的区分——目前都没有。要动，就是新增机制，先与需求方确认。

## 5. 局内进出：依赖账本（§5.6）

承诺能成立的前提，是"**无人依赖**"必须是一个**可证伪的断言**。承重机制就是依赖账本。

### 账本语义

- **插件实例**每完成一次服务解析（`Get` / `TryGet`）落一条边 `(消费方实例 → 提供方实例)`。
- 账本由 `PluginHost` **进程级**持有，边带 `PodIndex` 归属，`DestroyPod` 时整批清零。
- **宿主的解析不落边**：宿主没有可供执法的声明清单（"凭声明"对根 Context 无定义），而落了解不开的边会让任何被主循环碰过的插件**永远不可热卸**。宿主的防线就是"每次现取、不缓存"那条纪律。
- **事件订阅不进账本**——订阅是订阅方的 Effect（出边，由 `EffectScope` 兜底），不产生"别人依赖我"的反向边。
- **粗粒度是刻意的**：哪怕消费方只是"调用一次就丢引用"，声明边照样拦 Eject。细化（瞬态解析自动过期）是复杂度的黑洞，档 ① 不需要它。

**两条规则互相锁死：**

1. **解析必须凭声明。** `ctx.Get<S>()` 只允许发生在 P 已声明依赖 S 的提供方之上；未声明的解析走"编程错误"路径，当场被拒。**这条堵住账本最大的洞——隐藏边。**
2. **边随解析建立、随实例销毁消失。** 提供方被卸前，账上只要还挂着一条边，卸载即被拒绝。

### 判定流

```text
EjectPlugin(pod, T)                        AdoptPlugin(pod, X)
 ① 账本查边：有人依赖 T？                    ① 就地重读 X 的清单（局部单点 Refresh，
    有 → 拒绝，报告点名每个消费者                      不吃旧快照）
 ② 无 → 销毁 T 的实例（Effect 逆序回收，      ② 二进制已驻留？是 → 复用镜像，但先做档三
    复用 §7.x 机器）                                    身份比对 —— 与磁盘不符 → 拒绝，
 ③ 卸载二进制 → 三档证据链（§8.2）                       提示「先全部 Eject 再试」；
 ④ 账本与活集合摘除 T                                    否 → 加载 + HeaderVersion / 清单校验
                                                   ③ X 声明的每条依赖都能绑定到活集合？
                                                        不齐 → 整体拒绝，报告缺哪条
                                                   ④ X 装配进当前 Pod，其出边落账
                                                        （①-④ 任一步失败 → X 干净退出，无人受累）
```

**M1 落地形态**：拒绝只在 `Error::Message` 里（子串是契约），**报告只在成功时存在**。`EjectReport` / `AdoptReport` 的字段定义在 `Include/Vase/Host/Evidence.h`。

### 四条规则

| # | 规则 | 理由 |
|---|---|---|
| ① | **入局必凭全量声明** | 声明依赖绑不齐活集合即整体拒绝。不带病入局，没有"先挂着等依赖"的中间态 |
| ② | **入局者皆为叶** | 已活插件的声明集不可更改 → X 在被采纳那一刻没有入边。推论：**Adopt 失败零级联**——递归拆除机器对 Adopt 路径备而不用 |
| ③ | **离场必为叶** | 以账本反查为准，哪怕一条声明未用的边也拒绝。**没有强制模式**——强制拆边就是级联重启，已明文否决 |
| ④ | **全程串行于 Host 线程** | 不存在"Eject 撞上半程 Adopt"的交叠态，状态机不需要并发守卫——这是平台难度预算里省得最狠的一条 |

### 四条补角

- `DestroyPod` 时 Adopted 节点**没有特殊位置**——出边足以让它在活集合的逆拓扑序里领到自己的拆位，与批装载节点同一台机器；
- **`Failed` 状态的插件可以被 Eject**（拆的是记录与驻留镜像，无实例、必无入边，报告注明）；
- **Adopt 不改 Preset**——X 留在插件目录里，下一局自然编入。"临时试试即弃"是宿主的目录管理问题，Vase 不设 `temporary` 标志；
- Adopted 插件的配置走**同一套三层合并**——热插件没有自己的配置通道。

### 两个明确的不管（防过度承诺）

- 宿主的解析不落边，其缓存指针账本更看不见——**插件侧靠"凭声明"执法，宿主侧只有纪律，这是不对称的设计决定而非缺口**；
- 经由**进程级状态**中转的"语义依赖"在图上同样不可见——靠显式的进程级状态登记 + `EjectReport::ProcessStatesReset` 提示面兜底。

**本节没有引入 epoch。** "依赖集变了没"不做指纹判定，只有"进出那一刻账上有没有边"这一个判定。

## 6. 三档证据链（§8.2）

v2 的卸货发生在四下无人的静默期；**v3 的 Eject 发生在别的插件还在跑的现场**。证据从一条变三档，每档各自可证伪，由 `PluginHost` 在 Eject / Adopt 时主动执行并写进报告：

```text
档一 · 实例归零   三平台同：账本无反向边 + EffectScope 空 + 存活对象计数 0。
                 计数非零即拒卸——POCO 对此只留了一句源码注释警告调用方，v3 把它升格为机制。
档二 · 映射解除   Windows：FreeLibrary 后文件可覆盖写——**辅助判据**（抓引用计数残留够快够准，
                        但会被"改名替换"骗过，且探针与重载之间有 TOCTOU）。
                 Linux：  dl_iterate_phdr 条目消失（主判）。
                 macOS：  _dyld_image_count / 路径枚举条目消失。
档三 · 新代码生效  内存镜像身份特征 ↔ 磁盘文件身份特征 比对。
                 Adopt 内部默认执行，**复用驻留镜像的分支同样比对**。
```

**档一、二可以全绿，只有档三分得出新旧。** Windows 的定位随之调整：档二降辅助，档三（RSDS）升**主判**——"唯一不可伪造"那句话已被"改名替换"证伪。身份特征的构建要求见 `abi-boundary.md` 第 5 节。

**档三失败的政策**：Adopt 失败，X 留在局外，局内其余插件健康无恙；报告明文给出标准逃生门——**重建整局**。不自动重试（掩盖不确定性），不自动重建局（违背"失败显式报告"）。

### 判据力按平台不对称（写进结构）

`UnloadEvidence` / `EjectReport` 里成对出现 `MappingRemoved` 与 `ReopenWritable`，外加 `MappingRemovalIsObservable` / `ReopenWritableIsMeaningful`：

> **缺一个平台字段的"成功"比失败更危险。** 读报告的人不必背文档就知道哪个字段在本平台有判据力。

`BinaryActuallyUnloaded` 为 false 且无错误 = **其他 Pod 实例仍活，货留在架上**——这是正常结果，不是失败。

## 7. 改这块之前必须知道的三件事

1. **驻留与卸货是两回事。** "一文件一记录"：`EnsureResident` 对本实例的同一绝对路径只调一次平台加载。**卸货只发生在 Eject / Shutdown，`DestroyPod` 不卸货**（§8.1）。
2. **`Loader::FindResident` 的查询键是字面比较**，而表里存的是**绝对化后**的路径——拿相对路径查会查不到刚存的那条。调用方请自己先绝对化。
3. **EdgesTo / EdgesFrom 返回的指针指进账本内部存储**，下一次改动即失效——查到就当场读，别存过界。

## 8. 未落地的部分（别当成已有能力）

- **级联热替换 / 强制 Eject（档 ②）**：v3 只放行叶节点。**叶热替换已是核心承诺，级联热替换仍然不做。**
- **epoch / 全量 HMR / 依赖方原地重绑定（档 ③）**：账本从源头拒绝制造上下线。
- **配置（`VASE_CONFIG`）与进程级状态（`.ProcessState`）**：`EjectReport::ProcessStatesReset` **M1 恒空**，登记属 M3。
- **清单 / Preset / `PluginCatalog` 求解链**：M2。M1 的 `LoadPlan` 是手写 struct（D12），"M1 无清单，以计划登记代替"（`PluginHost::KnownBinaries`）。
- **移动端**：Android / iOS 上的任何热插拔都不做，档 ① 也不给例外（Apple 平台禁下载代码 dlopen）。

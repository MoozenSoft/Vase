# VasePack N:1 清单与装配链：设计 spec

**状态：需求方于 2026-10-13 确认 grilling 的 Q1–Q17 与最终整体设计；尚未开始产品实现。**

分支：`vasepack-n-to-one`，起点：`0b22388`。已确认：同时覆盖动态组合库与静态链入；一包一目录，固定使用 `pack.json`，内含 `plugins` 数组；`plugin.json` 与 `pack.json` 分别描述单插件和组合库，用途不同、并行存在。

工程规则、命令与验证基数以根 `CLAUDE.md` 为准。前两波的 D203/D226 排除 N:1 属历史波次范围，本波单独处理该项；真实移动工具链和移动交付产物仍在本波之外。

**既有实现依据**：`PluginCatalog::Refresh` 只扫子目录中的单插件清单；`ParseManifestFile` 返回一个 `ManifestEntry`；`RunScan` 与 `ValidateDirectory` 要求恰好一个描述符；`PluginCatalog::Solve` 只生成文件来源。另一方面，Host 已能按 Id 查询组合库，并接受 `BinaryPath` / `InProcessEntry` 两种来源。因此本波主要补清单、发现、求解和工具链，复用现有装配机制。

**方案取舍**：需求方已选一库一份包清单，来源只写一次、成员集可以双向校验、整份文档原子更新。每插件一份清单会重复来源且留下跨文件一致性问题；静态包仅依赖编译期描述符则会形成两条发现链，不能共用零装载的 JSON 分析规则。

## 1. 交付行为与边界

发布清单给出一份组合库里的全部插件；宿主通过 Catalog 按插件 Id 应用 Preset、合并配置、求解依赖，再从同一份分析结果生成现有 `LoadPlan`，交给现有 `CreatePod`。宿主提供的是库级来源，不能再维护一份库内插件 Id 列表。

动态包从文件加载。静态包由宿主显式绑定已链接的查询与枚举入口，支持同一宿主内多个静态包；条目装配仍使用现有 `InProcessEntry`。JSON 不保存地址，静态归档不进入动态加载器。

交付包含调用者可复用的清单生成与 staging 接口，以及显式 CMake 构建目标。完整生成/发布链不能只存在于测试 fixture 中；调用者给出包目标与输出目录即可使用，成员 Id 从描述符取得。

本波以桌面八线验证这条共享链路，不把桌面结果表述成 iOS/Android 已验证。不改进程级/实例级分层、服务注册通道、依赖账本或关停时序，不增加移动端热插拔、CI/CD、对外分发、强制 Eject 或级联热替换。

## 2. 清单格式

### 2.1 包清单

包清单固定命名为 `pack.json`，位于传给 Catalog 的根目录下的一级包子目录。它描述组合库，`plugin.json` 描述单插件；两者分别管理格式版本，不构成升级或替代关系。包清单首版为整数 `schemaVersion: 1`。顶层键白名单为 `schemaVersion`、`sourceId`、`source`、`plugins`。

动态包最小示例：

```json
{
  "schemaVersion": 1,
  "sourceId": "VasePlugins",
  "source": { "kind": "dynamic", "binary": "VasePlugins" },
  "plugins": [
    { "id": "Vase.Hello", "enabledByDefault": true },
    { "id": "Vase.Dependent", "enabledByDefault": true }
  ]
}
```

这只是格式示例；实际生成物须含描述符元信息，依赖和配置不从示例推断。

静态包的同一份插件数组使用 `"source": { "kind": "inProcess" }`。`sourceId` 为宿主绑定的逻辑标识，不是 `.a` 路径，也不是插件 Id。

规定：

- `sourceId` 非空，限 ASCII 字母、数字、点、下划线与连字符，排除 `.` 和 `..`；一个快照内唯一。内部单插件来源使用独立保留命名空间，不与它冲突。
- `source.kind` 只接受 `dynamic` 或 `inProcess`。动态来源必须有合法本平台 binary stem，不能含路径；其实际文件与 `pack.json` 同处包目录。进程内来源拒绝 `binary` 字段，避免把归档误当可加载文件；静态包目录可以只含清单。
- `plugins` 为非空数组；每项有非空且唯一的 `id`。插件元信息支持 `displayName`、`version`、`enabledByDefault`、`requires`、`optionalRequires`、`provides`、`config`、`processStates`，默认值和语义与单插件清单中的对应字段一致。成员拒绝 `schemaVersion`、`binary` 与来源字段。
- 未知字段、非整数版本、未知版本、非法类型、重复 Id 均返回带文件和成员归因的 `Err`。字段语法解析与依赖/配置语义求解仍分层处理。
- 写出按插件 Id 排序。数组中其他有既有语义的顺序维持原规则；不能把全部数组无差别排序。

### 2.2 单插件清单与包清单的分工

`<根>/<子目录>/plugin.json` 描述一个插件及其独立二进制，其解析与写出接口、格式和默认规则保持现有行为。`<根>/<包目录>/pack.json` 描述一份组合库及其成员，由独立解析/写出接口处理。`ParseManifestFile` 继续只返回单个插件条目。

两种用途的文档归一化到同一快照：插件条目按 Id 排序，库级来源单独拥有，条目关联来源。现有公开条目的 `Subdirectory` / `Binary` 在单插件清单中仍有原意义；包条目的来源通过新增查询接口读取，工具与 Catalog 内部不再从这两个字段猜包路径。

## 3. 发现与发布目录

`Refresh` 按名字排序扫描根目录下的一级子目录：有 `plugin.json` 时按单插件清单读取，有 `pack.json` 时按包清单读取。同一子目录同时存在两者时返回带目录名的 `Err`，不隐式设优先级；两者均缺时沿用 warning + 跳过规则，消息点名缺少这两类清单。

一个包目录只有一份 `pack.json`；包目录名不要求等于 `sourceId`，后者仍为逻辑来源标识。根目录中的清单文件不参与发现，多包通过不同子目录承载。例如：

```text
发布根目录/
├── PackA/
│   ├── pack.json
│   └── 组合库文件
└── PackB/
    └── pack.json       # 静态包：入口由宿主绑定
```

不会遍历根目录的所有 DLL/so/dylib 来猜插件，也不递归扫描。框架库、普通静态库与 `pack-objects/` 里的链接输入不因此成为发布来源。

来源表记录文档位置、来源种类、动态文件路径和成员集合；插件快照记录每个插件的元信息和所属来源。来源表是来源事实的唯一维护处。快照、来源表与 Warnings 作为一个事务替换；失败保留旧三者。

整个快照中重复插件 Id 继续拒绝，即便一份来自单插件清单、一份来自包清单，或者其中一份包最终被 Preset 全禁用。包的重复 `sourceId` 也拒绝。构建时允许一个成员参与不同备选包，运行目录负责选取无重叠 Id 的组合；Preset 不负责为同一 Id 选择来源。

动态记录沿用 Loader 的绝对路径识别，不新增符号链接解析或文件身份去重承诺。一包一目录、固定清单名和无路径 binary 已排除普通发现路径中“两份清单引用同一绝对路径”的形态；不为该不可达形态新增验收负例，也不把不同路径的文件别名声称为已识别的同一物理库。

发布链路使用独立 staging 根，每个选定包各有子目录，动态包的库文件与 `pack.json` 同处；必要的框架运行依赖按平台加载契约安排，不把开发形插件子目录一起拷进去。测试 staging 由 fixture setup 显式构造，不能依赖整棵 build 目录恰好没有重复 Id。现有开发产物布局和平铺的组合库构建输出规则继续保留：构建输出与发布 staging 是两个位置，通过显式拷贝形成包目录；不把 STATIC 归档从链接输入目录搬成运行期加载文件。动态闭环必须从 staging 的实际包路径加载，验证移位后的依赖解析。

### 3.1 显式生成与 staging 目标

CMake 提供可复用接口，接收包目标、`sourceId`、包输出目录及显式运行依赖，建立生成与 staging 目标。该目标由调用者显式构建，不把发布写盘藏进普通 build 的 POST_BUILD。成员、描述符符号和动态/静态形态从包目标获得，不让调用者重复列出成员 Id。

动态生成器读取实际组合库的描述符；静态生成器显式链接对应包、引用生成的查询/枚举入口。两者使用共用的物化与校验件。该可复用生成器是交付能力，测试链接它建立证据；不新增独立 `Tools/VasePack` 产品工具，不把某个包的地址编进普通 `VaseCli`。真实移动端的交叉构建执行方式在移动波次设计。

每个成员已声明的源码 `plugin.json` 仅提供 `enabledByDefault` 策略；描述符决定 Id、展示字段、版本、依赖、配置定义/默认值与进程级状态。明确没有成员源清单时默认启用；声明的源清单缺失、解析失败或 Id 与对应描述符不符时生成失败。源清单全部成为显式构建依赖，单独修改策略也会重生成；staging 中已有的 `pack.json` 不作为此构建目标的输入。运行时启用和配置覆盖仍由 Preset / LoadRequest 承载。

指定的包 staging 目录完全归生成目标管理，调用者自己的文件放在该目录之外。先在同一文件系统的临时目录生成完整清单、复制所需动态文件并完成交付检查，全部成功后替换原包目录；生成、复制或安装失败时保留原目录内容，安装流程如已移开原目录须恢复。成功替换会清除过期库名和运行依赖，不做仅覆盖拷贝。

替换以单个包为单位，不承诺多个包共同提交，也不承诺并发读者在目录替换期间始终可见。静态包 staging 放清单，静态归档继续通过 CMake 目标供宿主链接。只有整个目标成功才报告 staging 可用。

## 4. 数据分析与可执行计划

### 4.1 共用分析

增加 Catalog 的纯数据分析入口 `Analyze(request)`，返回拥有形分析结果：插件级顺序、load/skip 决策与原因、来源标识、已合并配置、逐插件期望和 Notes。该结果不含描述符指针或入口地址。

`Analyze` 和现有 `Solve` 共享同一套内部参与判定、依赖闭包、冲突检查、拓扑排序、配置合并和归因算法。`Analyze` 不装载库、不调用入口、不依赖静态绑定。现有确定性、错误/跳过区分及 Notes 去重键契约不变。

新分析结果避免使用残缺 `LoadPlan`：不能为了让 CLI 展示静态计划而生成“两来源都为空”的 kLoad 条目。

### 4.2 来源绑定

保留 `Solve(request)`，新增接收静态来源绑定集合的重载。现有调用通过空集合委派，单插件动态来源的行为不变。绑定项含 `sourceId`、查询入口 `PluginEntryPoint` 和枚举入口，只在本次同步调用借用；产出的计划复制函数指针。Solve 不执行这两个入口，仍为纯数据处理。

动态条目填 `BinaryPath`、`InProcessEntry == nullptr`。静态条目填 `InProcessEntry`、`BinaryPath` 为空。两者配置和 `Expected` 都来自同一分析结果。Catalog 生成的包计划另携带拥有形的整包成员期望、来源与条目关联、以及静态枚举入口，供 Host 预检；该信息包括被跳过的包成员，不能只保留本次 kLoad 集合。

绑定规则：重复 `sourceId`、查询或枚举入口为空、指向未知或动态来源的绑定均拒绝；不同来源标识绑定同一个查询入口也拒绝。任何 kLoad 静态条目缺完整绑定时，`Solve` 返回 `Err`，点名来源和插件；不尝试查同名文件或进程符号。全部静态成员被跳过时不要求绑定，跳过条目不触发装载。

现有 Solve 产物中 `LoadPlanEntry::Id` 的快照借用窗口继续保持，避免借用临时分析结果中的字符串。`Expected` 与配置仍自持。快照 Refresh 后的旧计划使用纪律不变。

### 4.3 Host

`CreatePod` 对 Catalog 生成的包计划，在创建 Pod、执行 Stage0、创建插件或配置实例、调用 OnLoad/OnStart 之前完成整包预检。只检查至少有一个 kLoad 成员的包；参与包内被禁用或因依赖跳过的成员仍全部检查。全跳过包不加载、不要求静态绑定、不执行入口。独立 validate 不使用这个参与过滤，仍检查目录中的全部包。

每次 CreatePod 都按来源去重，在当前 Host 实际持有的镜像上枚举并核对 Id 集双向等值、查询/枚举一致性、HeaderVersion 和逐成员 `CompareDescriptor`。不缓存“上一局校验通过”，预检与随后的装配使用同一镜像。缺成员、多成员、重复或漂移导致整局 `Err`，带来源/插件归因；不交付部分装配的 Pod。预检通过后复用既有按 Id 查询与装配机器，同库成员共享原记录，服务与配置按插件独立处理。

预检可能加载动态库，因而镜像的静态构造与 DllMain 可能执行；“尚未创建插件实例”不等于“没有任何装载副作用”。预检失败不新增 Pod、实例、Effect 或依赖边，不自动卸载已经装载的动态镜像，不重置进程级状态，沿用现有失败留架规则。失败局没有 Pod 句柄，不能通过该局 Eject 留架记录；最终 Host 关闭收走动态镜像。预检本身不扩大进程级状态表的登记范围，登记仍随实际装配发生。

插件自身 OnLoad/OnStart 的失败保留现有宽容/Strict 语义，不与包输入不一致混为一类。静态 Eject 早闸、Adopt 不接静态入口、DestroyPod 不卸货均原样。

Host 不解析 JSON 或扫描目录，只消费计划里拥有形的包期望。包来源、完整期望与条目关联缺失/自相矛盾时作为计划误用拒绝。手写 LoadPlan 保留低层逐条目语义与现有测试用途；未声明包期望的原始计划不宣称经过整包校验。Catalog 生成包计划不能落入该旁路来逃过预检。

## 5. 描述符物化与工具能力

### 5.1 静态枚举的显式入口

新增枚举入口函数指针别名，签名与既有 `VasePlugin_Descriptors` 相同。新增接收该指针的 `InspectDescriptors` 重载，复用现有空表/null/版本闸检查；动态 `BinaryRecord` 读法调用同一检查件。

STATIC 包的分发表生成 target 专属查询/枚举入口和对应声明头，保证同一宿主可分别引用、绑定多个包。入口名由生成器确定，名称编码或生成冲突必须响亮拒绝；调用者通过生成头取得入口，不自行拼符号名。SHARED 包仍导出既有 `VasePlugin_GetPlugin` / `VasePlugin_Descriptors`。不改变成员宏生成的描述符契约符号；同一成员可用于不同备选包，多静态包见证使用无重叠 Id 的成员集。

静态清单生成/校验调用者同时显式持有按 Id 查询入口与枚举入口，分别用于装配绑定和成员枚举。枚举入口不得通过 `Loader::Symbol` 的进程内来源分支偷偷获得；该分支当前只提供查询入口的边界保持不变。

描述符字段到清单字段的转换复用既有物化与字段规则。先在镜像驻留期深拷为拥有形包文档，再写盘；先检查描述符和 Meta 的有效性，再枚举/查表交叉检查每个 Id 对应同一描述符，并拒绝重复 Id、空 Id 和空 Meta。工具完整校验与 Host 预检共用成员检查规则，两个调用方各自管理镜像归属。静态生成器和见证程序直接引用生成的两个入口，不增加全局注册表或 linker whole-archive 开关。

### 5.2 命令矩阵

| 命令 | 动态来源 | 静态来源 |
|---|---|---|
| scan | 单插件目录模式保留；识别子目录中的 pack.json 并按源库更新。新增显式 `scan --package <动态库文件> --source-id <标识>`，固定写该文件同目录的 pack.json；其他库不参与成员发现，不能再要求目录仅有一个动态库 | 普通 CLI 不能扫描 `.a`。已链接该包的生成器/调用者通过共用物化件与显式入口生成清单 |
| validate | 按物理库一次枚举，检查清单↔描述符 Id 集双向等值，逐插件复用 `CompareDescriptor`，之后照旧检查依赖与服务前缀 | 普通 CLI 完成清单结构/依赖/前缀检查，但明确报告描述符校验无法执行并计入未通过；已链接调用者可显式提供查询/枚举入口完成完整校验 |
| plan | 改用 Analyze，保持零装载，输出决策与文件来源 | 同用 Analyze，输出 inProcess 来源及“执行时需宿主绑定”；分析成功不宣称已取得可执行计划 |
| doctor | 身份、写探针、锁和装载检查按物理源去重；根与各来源子目录的写探针照常，收集序仍把装载放最后 | 普通 CLI 的装载/版本校验缺少宿主入口，明确未通过；磁盘身份与文件锁不适用，根与静态包目录的元信息写探针照常。已链接调用者可完成版本检查 |

退出码继续采用项目现有三档：完成且全部适用检查通过为成功，检查失败或必需验证无法完成为未通过，用法/环境错误为环境档。每一项“不适用”与“无法验证”分开；后者不能当成功。普通 CLI 见到静态包的 plan 可成功，validate/doctor 的不完整验证应以未通过返回。

共用生成/校验件不绑定某个产品包，也不把测试入口地址编进普通 `VaseCli`。生产生成接口按 §3.1 提供；静态见证链接同一组共用件与静态组合库，显式传入入口，不另做一套仅供测试的生成流程。

### 5.3 scan 保真与失败

包内每个插件按 Id 与已有 `pack.json` 合并 `enabledByDefault` 等清单独有字段；描述符事实从当前二进制重新物化。原有成员删除、新成员加入和来源标识变化都明确报告；显式指定的 `sourceId` 为写出来源事实。

目录扫描不会仅因枚举出多个描述符就把单插件目录转换为包目录。无包清单的组合库由显式 `--package` 模式引导生成；该模式遇到 `plugin.json` 时拒绝，避免在同一目录产生两种清单。目录内已有 `pack.json` 的更新使用其中的来源信息，静态包的缺枚举能力仍按命令矩阵报告。

普通包 scan 按 Id 保留已有清单的 enabledByDefault，新成员默认启用。成功写出以整份包文档为单位，原子替换；包内任一描述符或物化失败时保留原文档，多个源之间按现有尽力而为语义推进。

损坏的 pack.json 默认报错并保持原文件，不能沿用单插件 scan 的自动恢复策略。显式包扫描可加 `--regenerate` 要求重建：不读取损坏文件中的策略，全部成员默认启用，并明确报告重置；运行时 Preset 不受影响。该选项不绕过描述符、版本或成员一致性检查，写盘失败仍保留原件，写成功后才报告 regenerated。此 CLI 行为与 §3.1 的构建生成有不同输入权威：构建目标始终读取成员源码策略，不读取 staging 产物；CLI 更新则保留当前可读包清单的策略。

## 6. 动态包的 Adopt 与热插拔边界

Catalog 的 `AdoptInto` 依据来源记录定位文档。独立插件重读其 `plugin.json`；包成员重读整份包文档并按请求 Id 定位，缺成员或文档结构/成员重复立即拒绝。调用 Host 时仍使用逐插件期望，不能用当前快照代替磁盘重读。

兄弟库导入检查按物理动态来源生成候选集：排除目标自己的物理文件，去重同包其他插件映射到的同一文件；不把静态来源当可导入的兄弟 DLL。库内插件之间仍只走服务解析，不能借组合后的物理共处扩展注册面。

本波不新增按包一键 Eject/Adopt，不承诺组合库成员可独立替换二进制。动态包成员共享镜像，已有全局持有者闸和驻留复用身份检查继续把关；替换文件必须先释放全部持有者。静态来源的 `AdoptInto` 明确拒绝，不能为它拼出空的磁盘路径。

## 7. 公共面与文档影响

新增包文档/来源记录、Analyze 的拥有形结果、静态双入口绑定、显式枚举重载，以及 LoadPlan 的整包拥有形期望和来源关联。具体字段排布在实施计划中列清，保留现有公开函数入口和原始计划用途。宿主/Catalog 面的结构变化按 ABI 增量记账；不改插件描述符布局、成员宏生成的描述符契约符号、Plugin vtable 或 kHeaderVersion。STATIC 分发表入口由固定名改为 target 专属名，属于本波明确变更；原静态调用材料同步使用生成声明头，SHARED 固定入口不变。

序列化与解析仍由 VaseCatalog 承载，nlohmann 不进入公开头或 Host；生成/检查控制逻辑仍在工具层。现有源码、生成 TU 的门禁规则沿用根 `CLAUDE.md`，不因它是生成物而排除。

设计通过并实现后，按最终行为更新根 `CLAUDE.md` 的项目状态及相关规矩、wiki 的 §8.1/§8.6/§11.1/§11.3/§13.2、必要的 Console 使用文档。历史 spec 用现状指针标注，不把曾经的范围排除改成永久禁令，也不把未来移动构建写成已完成。
